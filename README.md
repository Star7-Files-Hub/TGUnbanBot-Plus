## 与原项目的差异

相对原项目（[CMLiussss/CF-Workers-TGUnbanBot](https://github.com/cmliu/CF-Workers-TGUnbanBot)），本项目主要变更：

- **解封确认严格整句匹配**：用户必须复制粘贴完整提示语才能触发解封，禁止夹带任何额外字符（防广告号绕过）。
- **多群组支持**：`GROUP_ID` 环境变量支持逗号分隔多个群组，自助解封流程会遍历每个配置群分别处理；管理员鉴权采取「任一群管理员即可」的策略。
- **黑名单结构升级（向后兼容）**：从 `["123","456"]` 裸数组升级为 `[{id, reason, by, at}]` 对象数组，记录封禁原因、操作人、时间。旧裸数组数据自动归一化升级，零迁移。
- **D1 数据库（唯一存储后端）**：完全基于 Cloudflare D1 数据库，免费层每天 10 万次写入不会溢出。黑名单、清扫缓存、批量任务全部存 D1。<br>**修复（2026-09-21）：清扫缓存曾「只删掉最后几条」** —— 消息缓存表 `moderation_messages` 的剪枝原为**全表共用一个 200 行窗口**，bot 在多个群时这个窗口被各群瓜分，广告号在 A 群连发的消息会被 B/C/D 群的正常发言提前挤出缓存；清扫是**按 `mid` 查缓存**的，查不到的 ID 就永远删不掉（线上实测：连发 15 条只清扫掉最后 5 条）。现改为**按群剪枝**，每群各自保留最近 `max(MSG_CACHE_SIZE, 200)` 行。完整说明见「渐进式处置 → 为什么首次必须自己补清扫」。
- **`/blacklist` 命令**：管理员私聊查看当前黑名单（最多 30 条）。**排版为竖排分条**（本版重点）：旧版把 TGID / 原因 / 操作人 / 时间四个字段用 ` · ` 拼成一行，Telegram 按屏宽随机折行，其中 `anonymous_admin:-100xxx` 长达 30 字符、一出现整行就被撑爆。现在每条记录一段、字段各占一行，折行位置固定。<br>时间从 `2026-09-02T23:40:47.004Z` 压成 `2026-09-02 23:40:47`（保留到秒，同一分钟内批量加黑仍能分出先后）；操作人翻译成可读角色（`匿名管理员（来源群 -100xxx）`、`系统自动`、`👑 主人` / `👤 副主人` / `🛡️ 超级管理员`）。<br>**操作人尽量做成可点击**：官方 `ChatFullInfo.has_private_forwards` 说明，对方若把「隐私和安全 → 转发消息」设为非「所有人」，`tg://user?id=` 链接只在与他本人的聊天里生效、别处退化成灰色死文本（管理员常改这项，于是出现「被封的广告号能点、管理员点不动」）。因此改为**优先输出纯文本 `@username`** —— Telegram 自动识别，不受该设置影响，与 `/admins` 同一套路子；同时保留 TGID 便于复制去 `/check`。没设用户名或查不到的仍回落 `tg://user?id=`。<br>用户名解析走 `getChatAdministrators` **按群批量拉取**（一次拿回整个群的管理员，而不是按人逐个 `getChat`），操作人去重后通常只有 2~5 个且几乎必然是管理员，因此 30 条记录也只需「配置群数」次调用；结果带 10 分钟运行期缓存，查询异常一律静默降级。
- **`/ban` `/spam` `/unban` 支持批量**：分隔符兼容半角逗号 / 全角逗号 / 空格 / 换行，也支持 `[123,456,789]` 数组外壳。三条命令统一使用安全预算：仅当 `U < 20`、`U × G <= 24` 且预计子请求 `<= 100` 时同步执行，否则自动创建 D1 批量任务并通过 Cloudflare Queues 按安全分片续接；其中 `U` 是去重后的 TGID 数量，`G` 是配置群数量。三者单次最多输入 50 个 TGID，单条用法保持原样。
- **黑名单导出接口**：`GET /{TOKEN}/export` 浏览器直接看 HTML 表格（带搜索过滤），`?format=json` / `?format=csv` 下载完整数据，CSV 自带 BOM 让 Excel 不乱码。
- **全局黑名单真踢人闭环**：`/ban` `/spam` 加黑后会**立即遍历所有 GROUP_IDS 把人踢出群**（之前只写库不踢人）；`/spam` 还会删除被回复的垃圾消息；黑名单用户在群里发言会被实时拦截删消息+踢人；被人拉回群也会立即被踢回去；新增 `/{TOKEN}/purge` / `/{TOKEN}/purge/run` 默认分批清扫 `/ban` + `/spam` 存量数据。
- **`/ban` `/unban` `/spam` 群内可用 + 闪屏 + 私聊详情**：原项目 `/ban` `/unban` 强制只能私聊，本项目允许群内直接发命令；`/spam` 也升级为同款双通道。群内执行时机器人发短闪屏提示（5 秒自动撤回）+ 按 `OWNER_IDS` 规则私聊完整详情，既快又不污染群消息流；除 `/check` 外，主人/副主人/超级管理员/群管理员在群内发送的授权指令会自动撤回命令消息本身。详情含**命令来源 / 作用范围 / 执行原因 / 群名 / 群 ID / 失败原因 / 解决建议**（Telegram 英文错误自动翻译为中文）。
- **主人/副主人通知系统**（可选 `OWNER_IDS` 启用）：`OWNER_IDS` 第一个 TGID 是主人，后续 TGID 是副主人。主人收到全部通知；副主人只收到 `/ban`、`/spam` 这类加黑踢出通知。OWNER_IDS 留空 → 全局禁用通知,保持原行为。
- **`/help` 第一主人专属帮助(隐藏指令展开)**:第一主人**私聊**发 `/help` 可展开查看全部隐藏指令清单。清单里的命令一律写成**裸文本而非 `<code>`** —— Telegram 只把纯文本里的 `/xxx` 识别成命令实体并支持**点一下直接发送**，包进 `<code>` 就只能点击复制。主人可**私聊**发 `/admins` 查看当前主人/副主人/超级管理员权限名单。所有专属命令对普通用户、群管理员、超级管理员、副主人**完全无反应**(群内静默、私聊提示权限不足且不泄漏指令内容)。这些命令本就不注册到 BotFather 命令菜单,天然隐藏。
- **投票通过后被举报人昵称脱敏（借鉴 AI 版设计）**:广告号的昵称本身常常就是广告(如"广告位招租 @xxx"),投票通过后若原样展示,等于借 bot 的投票卡片把广告**再广播一次**。现在投票通过后昵称脱敏为"首字***尾字",仍保留 `tg://user` 可点击链接供管理员核对;**进行中/被否决/已到期一律显示完整昵称** —— 群成员必须看清目标才能判断怎么投。
- **重复举报预检**:目标**已在本群被封禁/禁言**且**已在 D1 全局黑名单**时,`/ad` 直接静默跳过,不再刷出一张注定通过的投票卡片。必须两个条件同时成立才跳过 —— 只满足其一说明处置还不完整(如已加黑但没踢掉),仍走投票把处置补齐。复用目标保护检查已查到的成员状态,不额外调用 Telegram API。
- **解封成功回执改造（主群 = 回家的入口）**:原文案是"请点击 `{username}` 返回群组",在**私有群**里会渲染成"请点击 `-1003904078173` 返回群组" —— 纯文本**点不动**,文案本身在骗人。更根本的问题是:本项目**解封走全群、封禁也走全群**,bot 无法知道用户原本在哪个群被封,"返回某个群"这个语义从一开始就不成立(原项目是单群才没暴露)。现在改为:① 告知**全部 N 个配置群组的限制已解除,可以正常发言**;② 主群定位为**联系管理员的入口**,以 Telegram **内联按钮**呈现(按钮文字 = 💬 + 群名),用户有疑问点一下就能进群找管理员;③ 结尾的风险提示保持不变。可用 `SELF_UNBAN_CONTACT_GROUP` 指定按钮指向哪个群(须在 `GROUP_ID` 内,否则回落主群)。链接来源:公开群用 `username`,私有群用 **`getChat` 已返回的 `invite_link`**(零额外 API 调用);两者都拿不到时自动换用降级文案并**不附按钮**,不再出现点不动的假链接。旧的自定义 `SELF_UNBAN_APPROVED` 里的 `{username}` 继续有效,不会因本次改动失效。<br>**2026-09-19 起**这个按钮的链接来源多了一个更高优先级的选项:`SELF_UNBAN_CONTACT_URL` —— 填了就**直接用这个链接**(典型用法是**频道私信**),不再走"主群群名 + 群链接"那套。原因是主群链接**依赖群成员身份**,而被全群封禁 + 拉黑的人恰恰进不去任何群;频道私信这类链接不依赖任何群身份,他照样点得到。这个入口同时用在了**黑名单拒绝回执**上(那条回执原来只写"请自行联系管理员解封"却**没给任何联系方式**)。留空 → 回落主群链接,行为与之前逐字一致。
- **动态群组:指令加群,不用改环境变量(本次新增)**:以往新增治理群组必须去 Cloudflare 后台改 `GROUP_ID`。现在**第一主人私聊** `/addgroup -100xxxx [备注]` 即可加群,`/delgroup` 移除,`/listgroups` 查看。**两套数据天然分离** —— Worker 无法写自己的环境变量,所以指令加的群只存 D1(`dynamic_groups` 表),不可能出现在 `GROUP_ID` 里;合并顺序固定「环境变量群在前、动态群在后」,**动态群永远不会顶替 `GROUP_IDS[0]` 主群**。合并点在 `isConfiguredGroup` 之上,因此其调用点(封禁/踢人/黑名单拦截/`/purge`/批量任务/`/ad` 投票)**全部自动生效**,无需逐处改动。
  - **三道硬校验**:① ID 必须 `-100` 开头的超级群组格式;② 不得与 `GROUP_ID` 环境变量重复(避免两套来源打架);③ **bot 必须已是该群管理员且具备「封禁用户」权限**(复用 `/purge` 预检),不满足直接拒绝并给出原因 —— 否则加进来只是个全程报错的死群。D1 里若出现非法 `chat_id`(手工改库/schema 漂移)也会被过滤,绝不进入 `GROUP_IDS`。
  - **fetch 与 queue 两个入口都必须合并**:`getBulkJobConfiguredGroupIds` 会用 `isConfiguredGroup` 重新校验任务里存的 `groupIds`,queue 入口漏合并会导致涉及动态群的批量操作**被静默丢弃**(任务显示成功但那些群实际未执行)。两处已同时接入。
  - **代价如实说明**:① 每请求多一次 D1 读(15 秒运行时缓存摊薄,稳定态普通群消息共 3 条 SQL);② **群数会线性放大所有全群操作** —— `/ban` 每群 +1 次 `banChatMember`,`/purge` 总任务数 = 黑名单条数 × 群数,批量任务 `U × G` 增大后会更早转为 Queue 异步。加到 20+ 群时建议实测一次批量 `/ban` 的耗时。
  - **移除 ≠ 退群**:`/delgroup` 只是不再治理该群,bot 仍在群内;要让 bot 退出请用 `/leavegroup`。
- **`/check` 双库独立查询与复制操作**：远程 GKY 封禁库和本地 D1 黑名单分别判断。仅 GKY 封禁时复制 `GKYbotSave\nTGID`；仅本地封禁时复制 `/unban TGID`；两边都封禁时同时显示两个复制按钮。任何一边正常、失败或记录不适用，都不会吞掉另一边符合条件的复制按钮。
- **GKY 命令仅由真人发送**：复制按钮只把文本放进剪贴板，机器人不会自动发送或执行。<br>**GKY 记录来自哪个群只决定语义、不决定给不给按钮**（与源项目对齐）：记录属于你的 `GROUP_ID` 配置群 → 按钮写「📋 点击复制 GKY 移出黑名单代码」；记录来自别的群 → 按钮写「📋 点击复制 GKY 添加**全局**白名单代码」，并额外提示该代码**对所有接入 GKYbot 的群生效、不只是你的群**，且不会改动你的 D1 黑名单。<br>两道限制仍保留：① GKY 返回记录的 TGID 与查询目标核对不上时不给按钮（否则会给错人加白名单）；② 查询来自非 `GROUP_ID` 群时只返回详情、不给任何按钮（避免把管理能力暴露给外人）。
- **D1 黑名单来源收紧（本版重点）**：D1 全局黑名单的**唯一写入来源 = 真人管理员 / 超级管理员 / 主人 / 副主人执行的 `/ban`、`/spam` 指令**（含 `/ban 123 原因`、`/spam 123 原因`、引用消息 `/spam 原因`）。以下情况**一律不写入黑名单**：① 真人在群里直接点 Telegram「封禁」按钮（原生封禁）；② 任何作为管理员的**第三方机器人**封禁用户（无论何种原因）；③ 第三方机器人冒发 `/ban`/`/spam`（命令入口已加真人防护，`GroupAnonymousBot` 匿名管理员视为真人放行）。进入黑名单后**永不自助解封**，只能由**群管理员 / 超级管理员 / 主人 / 副主人**用 `/unban 用户ID` 移除。
- **黑名单用户互动通知分两种（本版新增）**：黑名单用户与 bot 互动时主人会收到通报，且**按信号强度区分文案**，一眼能分清对方做了什么。<br>发 `/start`（只是打开了 bot，可能只是误触）→ `📬 黑名单用户打开了机器人 …… 尚未尝试解封`，**不拒绝他**，照常给介绍语；<br>发 `/unban` 或粘贴确认整句（真的在尝试解封）→ `📢 黑名单用户申诉 …… 正尝试自助解封但被黑名单阻止`，并被闸门拒绝。<br>两条通报都带出加黑方式 / 操作人 / 加黑时间与可直接复制的 `/unban TGID`。拒绝闸门只守在 `/unban` 与确认整句上，`/start` 作为自我介绍不设闸门 —— 闸门本身一点没削弱。
- **`chat_member` 事件订阅**：群内手动**封禁**（真人点封禁按钮 / 任何作为管理员的机器人封禁）**不再写入 D1 黑名单**，仅发审计通知告知主人；手动**解封**时，若对象仍在 D1 黑名单则**立即封回并通知主人**（群内手动解封无法绕过全局黑名单），仅非黑名单对象的解封做审计通知。
- **超级管理员权限分级**：新增可选 `SUPER_ADMINS` 环境变量。名单中的用户即使不是 Telegram 群管理员，也可使用 `/ban`、`/spam`、`/unban`、`/check` 等普通管理命令；复制按钮本身不执行命令，最终仍由发送命令时的既有权限校验决定是否生效。
- **去除作者私群硬编码回退**：原项目在群信息查询失败时会回退到作者私群名称 `CM技术交流群` / `@CMLiussss`，本项目改为中性默认值。

- **渐进式处置：首次只禁言，再犯才全群封禁（本版重点，详见 [渐进式处置](#渐进式处置)）**：广告自动判定的处置改为**两段式升级**。首次判定为广告时**禁言**（`restrictChatMember`，不踢出、不拉黑，人留在群里）—— **消息触发**只禁言触发群、**cron 主动扫描**禁言**所有治理群**（它扫的是从没发过言的人，没有「当前群」语义）；同时写入 D1 监控台账；该号此后在**任意治理群再次被判定为广告**（包括同群再犯），才升级为**全群封禁**并标记「已升级」，不再重复升级。<br>设计意图：广告号在 A 群发广告不必然代表它在 B/C 群也发了 —— 先按孤例处置，只有在别处再次露头才认定是惯犯、届时才动用全群封禁。<br>**为什么首次用禁言而不是封禁**：`banChatMember` 把人踢出群，而 `unbanChatMember` **不会把人拉回群** —— 封禁的误判代价不可逆，禁言完全可逆。首次判定是整条链上唯一可能出错的一步，所以把不可逆的动作留到确认之后。<br>**首次不写 D1 黑名单** —— 拉黑会让黑名单兜底拦截在他去别的群发言时删消息并封那个群，等于绕开「再犯才升级」直接做了近似全群封禁。代价是首次少了黑名单这层网，所以**禁言失败会自动退回封禁**（消息触发退回本群、cron 轨道退回全群）；同时因为禁言没有 `revoke_messages`，**消息触发的首次会额外清扫该号在本群的近期缓存消息（上限 20 条）**，避免前几条广告留在群里。<br>新增环境变量 `AD_BAN_SCOPE_MODE`：`progressive`（默认，上述行为）/ `global`（恢复旧的全群封禁，用于一键回退）。<br>⚠️ 代价如实说明：首次判定到升级之间存在时间窗口，该号若在其他群不再发广告，就不会升级。多群治理且希望「抓到一次就全网拉黑」的场景，直接把该变量填 `global`。<br>**主群（`SELF_UNBAN_CONTACT_GROUP`，默认第一个群）豁免全部自动处置**（禁言与封禁、黑名单兜底拦截、复入群拦截都跳过它）—— 它是被全群封禁 + 拉黑的人**唯一**还能联系到主人的通道；豁免只给自动判定造成的黑名单（`reason = ad_auto`），手工 `/ban`、`/spam` 照常覆盖主群。<br>**判定通知下方带两颗按钮**：左键 = 误判出口（等价 `/ignore`，**不含主群**），右键 = 全群封禁（人工路径，**含主群**）。仅第一主人能在自己的私聊里点。详见 [渐进式处置](#渐进式处置)。

- **username 维度精准化：只比对账号自身 handle（误封治理，本版重点）**：`username` 型指纹**不再扫昵称 / 简介 / 正文**，只与被检测账号**自己的 `payload.username`** 精确比对。<br>起因是线上四起误封：`#135`（得分 5）、`#132`（得分 2）、`#143`（得分 3）全部低于封禁阈值 7，却因指纹层「单条命中即定罪」被封 14 个群。根因是 `username` 型指纹权重 `0.8` 恰好触及 `AD_FINGERPRINT_BAN_WEIGHT = 0.8`，构成一条**绕过总分、绕过豁免词、绕过 P1 单业务词豁免的定罪通道**；而学习端把两类值都写进这条通道 —— ① 广告号自身的 username，② **正文里扫到的所有 `@提及`**。第二条最严重：广告号发言时艾特了主人，主人的 `@handle` 就被学进指纹库，此后**任何人艾特主人都会被封**（`#143` 的判定依据只有一行「+3 指纹库命中：@ym94203」）。举报者原文引用广告号 handle 来警示他人，也会被同一条通道反杀。<br>**曾短暂整体下线该维度，但 `/delword type:username` 预览显示 199 条里绝大多数是真广告号 handle，召回损失过大**，故改为精准匹配方案：<br>① 匹配端 —— `matchAdFingerprints` 里 `username` 型行不进 haystack（昵称/简介/正文一律不比对），只与 `payload.username` 归一化后**精确相等**才算命中。**「你是谁」能定罪，「你提到谁」永不定罪**，误封通道被结构性切断，正常人艾特广告号或艾特管理员都不受影响。<br>② 学习端 —— 只学**账号自身 handle**，`@提及`扫描路径**永久删除、不再恢复**；配额恢复 `username: 2`；入库前加 Telegram handle 格式校验（5-32 位、仅 `[a-zA-Z0-9_]`），过短或含中文等非法字符的一律跳过。<br>③ `/addword` 恢复接受显式 `type=username`。<br>回滚端 `markAdFingerprintFalsePositive` 保留完整 username 匹配能力 —— 那是纠错路径，要能识别并清掉历史脏数据。<br>测试覆盖「自身 handle 入库 + 边界格式剔除 + `@提及`不学」三类行为，并有断言钉死「艾特他人不被判定」。

- **广告指纹单业务词不封（P1 精度加固）**：指纹库命中后，若命中的全部指纹均为「单业务词」（如单独一个 `USDT`、`收购`），则不直接触发封禁，仅将这部分权重与**结构化评分**联合计算；只有同时命中其他广告词（多词共现）时才封禁。避免正常技术讨论、二手交易话题因包含单一业务词而误封。`evaluateAdSuspect` 里通过 `isSingleBusinessWordFingerprint` 标记 + `nonSingleMaxWeight` 分离逻辑实现，不影响多词指纹的正常封禁行为。
- **`/job` 私聊翻页改为 inline 按钮**：`/job 任务ID` 在私聊中查询批量任务详情时，用户列表超出单页（10 人）时原来用文本提示 `翻页:<code>/job 任务ID 页码</code>`；现改为直接在消息底部挂 inline 按钮，点按钮即编辑原消息跳页，无需手动输入命令。群内触发因为走审计包装路径、无法还原原始消息，保留文本翻页提示不受影响。
- **同款广告连带查杀（合并自原项目，详见 [同款广告连带查杀](#同款广告连带查杀)）**：第一主人引用一条广告 `/spam` 时，顺带把 **24 小时内、全部配置群**里发同款文案的账号一并处置（删消息 + 加黑 + 全群封禁）。为此 `moderation_messages` 新增 `text_hash`（FNV-1a 32 位）+ `text_norm`（归一化正文）两列，走哈希等值 + 时间窗口反查，一次 D1 查询跨群覆盖；`D1_SCHEMA_VERSION` 6 → 7。<br>**仅 `OWNER_IDS[0]` 可触发**（副主人 / 超管 / 群管理员的 `/spam` 照常执行本职，只是不连带，且完全静默）。**单次硬上限 20 个号**（子请求预算所限），同步/批量分流按预算动态判断，超预算转 D1 批量任务 + Queues。批量路径带 `deleteTargets` 逐条 `deleteMessage` —— `revoke_messages` 只撤 48 小时内且目标必须仍在群里，对「已冻结 / 已退群」的号完全无效。结果私聊第一主人并附**一键回滚 `/unban` 命令**。
- **逐字分隔混淆检测（合并自原项目，详见 [逐字分隔混淆检测](#逐字分隔混淆检测)）**：补回被删空的去混淆能力。广告号在汉字间插分隔符躲词表（`低.價.出.正.品`），现两路反制：① **结构加分**（正文 +4 / 昵称 +3，打规避行为本身、不依赖任何广告词汇）；② **去混淆文本参与词表匹配**（挂在唯一入口 `countAdKeywordHits` 上，一处改动覆盖结构评分 / 指纹抽取 / 豁免词 / 引用体查杀）。分隔符分 STRICT（点号、下划线等，中文不用它们断句）与 LOOSE（顿号、逗号，正规列举标点，只在严格逐字时才算混淆）两级 —— 否则「苹果、香蕉、橘子、西瓜」这类正常列举会被整片误伤。签名要求 ≥3 组连续且限定 CJK，英文缩写与版本号不受影响。
- **回复学习触发词收紧为完整短语（合并自原项目）**：`AD_REPLY_LEARN_TRIGGERS` 从单词（`'广告'`、`'垃圾'`、`'该封'`）**收紧为带明确判定意图的完整短语**（`'这是广告'`、`'广告号'`、`'该封他'`）。起因是线上事故：管理员回复一句含「广告」二字的吐槽，把得分 -1（远低于阈值 7）的人封了 14 个群 —— 确认分支**强制 `verdict='ban'`，得分完全不参与决策**。<br>连带把 `AD_QUOTED_KILL_NEGATORS`（**举报者保护名单**，用于识别「引用广告 + 回一句『广告』警示他人」并放行）与触发词表**解耦** —— 两表语义方向相反（前者漏词就杀错举报者必须宽，后者误触发就封错人必须严），原先后者写 `...AD_REPLY_LEARN_TRIGGERS` 展开复用，收紧触发词会连带打穿举报者保护。<br>另补两项可追溯性：① 触发回复原文（截 60 字）写进 `reasons` 随快照进 D1，`/pending` 与私聊通知直接可见（触发回复与被举报消息都会被删，群内零痕迹，否则只能翻 7 天就过期的 Cloudflare 日志）；② **斜杠命令文本永不进指纹库**（整段正文兜底与短语截取两条路径同时过滤）—— 线上事故里 bot 无权限删不掉 `/ban` 命令消息，命令文本被学成权重 1 的指纹，构成「管理员用 `/ban` 封人 → 命令文本入库 → 下次发相同命令即被秒封」的自噬循环。
- **`PROFILE_LOOKUP_GROUPS` 只读资料群（合并自原项目）**：新增环境变量，逗号分隔的群 ID，**仅用于 `/admins` 查询权限人资料，完全不参与治理**。以往权限人不在 `GROUP_ID` 配置群时 `/admins` 只显示「未获取」，唯一解法是把那个群加进 `GROUP_ID` —— 但那等于把封禁能力与命令权限一起开放给一个只想借来查昵称的群。现在填在 `PROFILE_LOOKUP_GROUPS` 里，其 Telegram 管理员不会获得任何权限，bot 在该群也**不需要管理员权限**（普通成员即可）。<br>连带修掉一个真 bug：`resolvePermissionUserProfiles` 第二条查询轨原写 `if (profiles.has(id)) continue`，而 `STATIC_USER_PROFILES` 在函数开头就把兜底资料填进同一个 Map —— 只要某人在静态表里有一条，实时查询轨就被整个跳过，「静态表只作兜底、查到实时资料就覆盖」这个承诺根本不成立（对方改昵称永远显示旧值）。现改为只跳过已由 API 查到的。
- **`/admins` 来源群显示群名并支持点击跳转（合并自原项目）**：来源群从纯 ID（`-1002565053719`）改为「群名（ID）」。群名可点击直达：公开群走 `t.me/username` 永久链接，私密群需 bot 为该群管理员才有邀请链接，拿不到就只显示群名。<br>**刻意不调 `exportChatInviteLink`** —— 那会撤销并重建群主邀请链接，让群内所有人手上的旧链接失效，代价远大于「让一行字可点击」。ID 始终保留（排查时要复制的是它）。群资料按 ID 去重缓存，只查实际出现在名单里的来源群。

> 全局黑名单语义：D1 中的黑名单是**永久全局黑名单**，**唯一写入来源是真人用 `/ban`、`/spam` 指令**；真人群内手动封禁、第三方机器人封禁一律不写入。命中后自助解封流程第一道闸即拒绝，复制或发送 `GKYbotSave` 只处理 GKY，不会清除本地 D1；群内管理员手动解封也会被立即封回并通知主人。只有**群管理员 / 超级管理员 / 主人 / 副主人**主动用 `/unban 用户ID` 指令才能从黑名单移除。

## 功能

### 普通用户

- `/start`：展示**机器人介绍欢迎语** —— 说明这是什么 bot、能做什么，并引导被封用户去发 `/unban`。**刻意不含解封确认整句**（那句口令只在 `/unban` 出现），因此第一主人在群里发 `/start` 也不会把口令贴进群。文案可用 `START_WELCOME` 环境变量自定义。
- `/unban`（不带参数）：展示自助解封检查清单与确认整句，这是被封用户的自助入口。
  - ⚠️ **群里发 `/start` 或无参 `/unban` 只有第一主人能触发**。任何其他人（普通成员、群管理员、超级管理员、副主人、匿名管理员）在配置群里发，机器人**纯静默** —— 不回、不撤回命令、不私聊主人，一次 Telegram 请求都不发。私聊行为不受影响。
- 复制粘贴指定整句确认文本：自动检查用户在每个配置群内的状态，分别尝试 `unbanChatMember` / `restrictChatMember`，并返回逐群结果。
- 用户存在 GKY 封禁记录时，自动在主群 @管理员 进行二次审核。

### 群管理员（任一配置群管理员即生效）

| 命令 | 使用位置 | 说明 |
| --- | --- | --- |
| `/ban 用户ID [原因]` | 私聊 / 群内 | 加入 D1 黑名单（reason=manual）+ **遍历所有 GROUP_IDS 真踢出群**。支持单个、批量与原因：`/ban 123 广告引流`、`/ban 123,456 批量广告`、`/ban [123,456,789]`。小操作量即时执行；20 个及以上 TGID，或多群下总操作量过大时，自动创建 D1 批量任务。群内授权管理员发送后，机器人会撤回命令消息本身，并发闪屏 + 私聊详情。<br>**群内对单个 TGID 执行时还会清扫当前群**（本版新增，与 `/spam` 对齐）：Telegram 的 `revoke_messages` 只对**仍在群里**的成员生效，目标若已退群或已被别人踢过就变成预封、历史发言一条都撤不掉，因此额外从 `moderation_messages` 捞出该 TGID 在当前群缓存的消息 ID 逐条删除，上限 `max(MSG_CACHE_SIZE, 200)` 条。<br>⚠️ 私聊 `/ban`（没有「当前群」概念）与批量 `/ban`（N 目标 × 200 条会撞 Cloudflare 子请求上限）**都不做**这层清扫，大范围清理请用 `/purge`。 |
| `/unban 用户ID` | 私聊 / 群内 | 从 D1 黑名单移除并遍历所有 `GROUP_IDS` 解封。**支持批量**：`/unban 123,456,789` 或 `/unban [123,456,789]`（半角 / 全角逗号 / 空格 / 换行均可，单次最多 50 个）。小操作量即时执行；达到 20 个 TGID、群操作数超过 24 或预计子请求超过 100 时，自动创建 D1 批量任务并通过 Queue 续接。群内执行时同样发闪屏 + 私聊详情。 |

| `/job 任务ID [页码]` | 私聊 / 群内 | 查询 `/ban` `/spam` `/unban` 自动创建的 D1 批量任务状态。主人查看普通 `/job` 时按每页最多 10 人按需查询用户资料；`/jobrun` 和 Queue 执行阶段不查询姓名。群内查询会发闪屏并按通知规则私聊详情。 |
| `/jobrun 任务ID` | 私聊 / 群内 | 手动补跑未完成的大批量任务。正常情况下 D1 批量任务会自动分阶段续接到完成，`/jobrun` 仅作兜底。 |
| `/check` | 群内回复 / 私聊 | 同时查询远程 GKY 封禁库与本地 D1 黑名单。两种用法：**群内回复**某条消息发 `/check`；或用 `/check TGID`（私聊或群内均可）。配置群记录按状态提供纯复制按钮：GKY 封禁复制 `GKYbotSave\nTGID`，本地封禁复制 `/unban TGID`，两边封禁显示两个按钮；非 `GROUP_ID` 来源群只查询。结果附带本地加黑方式 / 执行原因 / 操作人 / 时间。 |
| `/blacklist` | 私聊 | 查看当前 D1 黑名单（最多显示 30 条） |
| `/ad [原因]` | **仅群内回复** | 回复某条广告消息发起**隐藏举报投票**。赞成与反对**共用同一阈值 6 票**（`AD_VOTE_THRESHOLD`）：赞成先达 6 票 → 加黑 + 全群封禁 + 删除被举报消息；反对先达 6 票 → 否决不处理。任一配置群管理员点赞成或反对即**一票定音**立即结束；发起人自己点反对视为**放弃举报**并关闭投票。命令消息发出即被删除（隐藏痕迹）。发起人自动算 1 票赞成，支持改投与去重。<br>⚠️ **本命令始终走全群封禁**，不受 `AD_BAN_SCOPE_MODE` 的渐进式策略影响 —— 它是真人集体认定，与自动判定的孤例处置不同级。<br>**目标保护**：不能对自己、机器人、任一配置群管理员发起。<br>**重复举报预检**：目标已在本群被封禁/禁言**且**已在 D1 全局黑名单时静默跳过（两个条件必须同时成立）。<br>**投票通过后昵称脱敏**为「首字\*\*\*尾字」，避免借投票卡片二次传播广告；进行中/被否决时显示完整昵称（群成员要看清目标才能判断怎么投）。<br>普通成员默认不可发起，需第一主人用 `/add_ad_admin TGID` 授权。 |
| `/start check_用户ID` | 私聊深链 | 二次审核入口，由机器人自动生成链接 |

> 说明：`[123,456,789]` 数组外壳只用于粘贴批量 TGID，里面不解析原因；需要写原因时使用普通格式，例如 `/ban 123,456 批量广告`。`/job` 与 `/jobrun` 可直接发送使用，但不注册到 BotFather 命令菜单。群内授权指令除 `/check` 外都会撤回命令消息本身；普通用户无权限命令不处理。

### 超级管理员

`SUPER_ADMINS` 环境变量配置的 TGID 拥有普通群管理员命令权限，即使账号不是任一配置群的 Telegram 管理员，也可使用 `/ban`、`/spam`、`/unban`、`/check` 等命令。`/check` 的复制按钮不会自动执行任何操作，因此不再存在单独的按钮点击权限。

### 主人/副主人专属(`OWNER_IDS`)— 隐藏指令

仅 `OWNER_IDS` 配置的主人/副主人可用。**对普通用户、群管理员、超级管理员完全无反应**(群内静默、私聊提示权限不足),且这些命令不注册到 BotFather 命令菜单,天然隐藏。主人/副主人**私聊机器人**发 `/help` 可随时展开下表:

| 命令 | 位置 | 说明 |
| --- | --- | --- |
| `/help` | 私聊 | 展开全部 OWNER_IDS 专属隐藏指令清单 |
| `/admins` | **仅主人私聊** | 查看当前 `OWNER_IDS` / `SUPER_ADMINS` 权限名单，显示 TGID、昵称、用户名、群内身份、来源群（群名可点击跳转）。群内不支持且静默。<br>⚠️ 昵称与用户名靠 Telegram API 实时查询，而 API **只能查到 bot 所在群的成员** —— 权限人若不在任何配置群里，只会显示 TGID 加「未获取」。三种解法：① **推荐**：把 bot 拉进此人所在的群（**普通成员即可，无需管理员**）并将该群填入 `PROFILE_LOOKUP_GROUPS`（只读资料群，**不会**给该群开放任何治理权限）；② 把该群加入 `GROUP_ID`（⚠️ 会连带开放封禁能力与命令权限，不推荐仅为查资料这么做）；③ 用 `STATIC_USER_PROFILES` 填静态资料兜底（写死值，对方改昵称不更新）。<br>**来源群链接**：公开群走 `t.me/username` 永久链接；私密群需 bot 为该群管理员才有邀请链接，否则只显示群名（刻意不调 `exportChatInviteLink` —— 那会撤销重建主邀请链接，让群内所有人的旧链接失效）。 |
| `/addgroup -100xxxx [备注]` | **仅第一主人私聊** | **不改环境变量、直接用指令新增治理群组**。写入 D1，与 `GROUP_ID` 环境变量分离存放（Worker 无法写自己的环境变量），但合并后享受**完全相同**的治理能力：黑名单拦截、复入群踢回、`/ban` `/spam` 全群封禁、`/purge` 清扫、批量任务。<br>三道硬校验：① ID 必须 `-100` 开头；② 不得与 `GROUP_ID` 环境变量重复；③ **bot 必须已是该群管理员且有「封禁用户」权限**（复用 `/purge` 预检逻辑），否则拒绝并说明原因 —— 加进来也只会全程报错。 |
| `/delgroup -100xxxx` | **仅第一主人私聊** | 移除指令添加的群。`GROUP_ID` 环境变量里的群**无法**用指令移除（会提示改 Cloudflare 后台）。移除只是不再治理，bot 仍在群内，需退群用 `/leavegroup`。 |

| `/leavegroup -100xxxx` | **仅第一主人私聊** | 让 bot 退出指定群。与 `/delgroup` 的区别：`/delgroup` 只是不再治理、bot 仍在群里，`/leavegroup` 是真的退群。 |
| `/add_ad_admin TGID` | **仅第一主人私聊** | 授权某个普通成员发起 `/ad` 举报投票（无需其为群管理员）。 |
| `/del_ad_admin TGID` | **仅第一主人私聊** | 取消该成员的 `/ad` 发起权限。 |
| `/pending [N]` `/ignore 序号` `/allowlist [del 序号]` `/rescreen [N]` `/adstats` | **仅第一主人私聊** | 广告检测复核与状态查询，见 [广告检测](#广告检测)。 |

### 自动化

- **新机器人风控**：所有配置群中，**新加入**的「其它机器人」若**不是管理员**则被自动全权限禁言。具体规则：
  - ✅ 触发：群里有人**新拉入**一个机器人，且该机器人不是群管理员
  - ❌ 不触发：群里**已存在**的旧机器人（不会回溯处理已在群成员）
  - ❌ 不触发：本机器人自己被加入群（不会自禁）
  - ❌ 不触发：新加入的机器人**已经是管理员**（拉进群之前就设为管理员可绕过禁言）
  - ❌ 不触发：新加入的是普通用户（非机器人）
  - 用途：防止有人偷偷把广告 / 拉群 / 转发类机器人拉进群里发广告，争取时间让群主决定是否踢掉
- **管理员手动操作同步**：群内手动 ban（真人点 Telegram 封禁按钮 / 任何作为管理员的机器人封禁）**不再写入 D1 黑名单**，仅发审计通知告知主人；要把人加入全局黑名单请用真人 `/ban`、`/spam` 指令。手动 unban 时，若对象仍在 D1 黑名单则**立即封回 + 通知主人**（全局黑名单不被群内手动解封清除），非黑名单对象仅做审计通知。移出全局黑名单请用 `/unban` 指令。
- **黑名单用户群消息拦截**：已在 D1 全局黑名单的用户，在任一配置群发言时机器人会**实时删除消息并踢出群**。管理员豁免（避免误加黑导致管理员被踢）。
- **黑名单用户复入群拦截**：已在黑名单的用户被人拉回群 / 自己加回群时（`chat_member` 事件 status 变为 member），机器人会**立即把他再踢出去**，无需人工介入。
- **广告号自动检测**：新成员入群与群内发言时自动过三层判定，总分达阈值即按[渐进式处置](#渐进式处置)策略处置（默认首次只**禁言**、再犯才全群封禁；消息触发只禁言触发群，cron 主动扫描禁言所有治理群；触发群是主群时整体豁免）+ 推快照给第一主人复核，通知下方带「误判放行 / 全群封禁」两颗按钮。管理层豁免、频道自动转发帖豁免、bot 不参与判定（交给新机器人风控）。详见 [广告检测](#广告检测)。
- **观察窗口**：得分介于观察阈值与封禁阈值之间的用户进入 24 小时观察窗口，不做任何处置。窗口内再次发言时**分数累加**，累加后达封禁阈值即处置 —— 一次擦边不封，反复擦边才封。第一主人可用 `/rescreen` 拿当前指纹库把窗口内的人重新筛一遍。
- **回复学习**：群管理员回复某条消息说「这是广告」/「封了他」→ 立即按广告处置并把该用户资料学入指纹库（manual 来源，豁免误报退役）；说「不是广告」/「误封了」→ 解黑 + 全群解封 + 给命中的指纹记误报。仅管理层可触发，目标是管理层时拒绝。

## 广告检测

> 本章描述 V2 广告号自动检测。**不绑 Workers AI 也能用**（自动降级为两层），**不用改环境变量**（全部有默认值），**不用手动建表**（首次触发自动建 11 张表并写入种子数据）。

### 三层判定怎么工作

判定对象是**用户身份 + 消息正文**：昵称、username、个人简介（bio）、消息文本、文本中的域名。三层得分累加，与阈值比较后决定处置。

| 层 | 判据 | 说明 |
| --- | --- | --- |
| ① 结构化评分 | 纯 JS 正则与关键词 | 对称 emoji 昵称（`💚高价收网赚号💚` 这类广告号最强的单一信号）、数字前缀昵称、交易动词（收购/代理/日结/秒结…）、非白名单域名、引流 `@账号`、敏感词变形（`网 du`、`USDT`）等。**零子请求成本**。<br>**协同分**：交易动词与业务关键词**同时**命中时额外 +2。单独出现「收购」可能是正常二手交易讨论，单独出现「USDT」可能是技术话题，但两类同现几乎必然是广告话术 —— 这条判据比统一提高单项权重或下调观察阈值精确得多，后两者会让正常用户成片进观察窗口。 |
| ② D1 指纹库 | 历史确认过的广告特征 | 四类指纹：`keyword` / `domain` / `username` / `bio`。命中加 3 分；权重 ≥ 0.8 的高置信指纹**单条即可定罪**。置信度低于 `AD_FINGERPRINT_MIN_CONFIDENCE`（默认 0.6）的指纹不参与判定。 |
| ③ AI 语义相似度 | `@cf/baai/bge-m3` | 把用户资料文本转成 1024 维向量，与样本库算余弦相似度。≥ 0.78 视为硬命中直接定罪；落在 `[0.65, 0.78)` 只加 2 分（软加分）。**未绑定 AI 时整层跳过**。<br>⚠️ **换模型必须清空样本库**：不同模型输出维度不同，旧向量无法与新向量比对。代码有维度守卫会跳过不匹配的向量并在 `/adstats` 提示，但那等于第三层可用样本变少 —— 换模型后请 `/clearsamples` 再 `/warmup` 重建。 |

判定结果三种：

- **总分 ≥ `AD_SCORE_THRESHOLD`（默认 7）** → 按下方[渐进式处置](#渐进式处置)策略处置（首次禁言、不拉黑；再犯才全群封禁 + 加黑）+ 生成待确认快照推给第一主人
- **总分 ≥ `AD_OBSERVATION_SCORE`（默认 5）** → 进入观察窗口，**不做任何处置**，窗口内再发言时分数累加
- **总分低于观察阈值** → 直接放行

**零成本预筛**：纯 JS 快速评分 ≤ 0 时立即返回，不拉取用户资料、不查指纹库、不调 AI。正常聊天的实际开销与未启用检测时相同。

**豁免清单**（这些一律不进判定）：主人 / 副主人 / 超级管理员 / 群管理员、已在黑名单的用户（走原有拦截逻辑）、机器人（交给新机器人风控）、频道自动转发帖、服务消息。

### 渐进式处置

由环境变量 `AD_BAN_SCOPE_MODE` 控制，**默认 `progressive`**。这是「抓到一次广告，要不要立刻在所有群拉黑他」这个问题的答案。

| 模式 | 首次判定 | 该号再次被判广告 | 台账 |
| --- | --- | --- | --- |
| `progressive`（默认） | **禁言**（不踢出、不拉黑）。范围看轨道：**消息触发**只禁言触发群并删掉触发消息；**cron 主动扫描**禁言**所有治理群** | 升级为**全群封禁**，标记「已升级」，此后不再重复升级 | 写入 `ad_ban_scope` 一行 |
| `global` | **立即全群封禁**（旧行为） | — | 不写台账 |

**两条轨道，两种「首次」**：广告自动判定有两条入口，它们的「首次禁言」范围不同 ——
- **消息触发**（群内发言判定、入群筛查、`/spam` 回复学习）：有明确的「当前群」，所以首次只禁言**触发那个群**。
- **cron 主动扫描**（`runAdBioRescan`，每天 2 次）：扫的是**从没发过言的人**，`chatId` 只是名册里记的最近发言群、**不是**当前群。这条轨道上的「首次禁言」= 禁言**所有治理群**（`muteUserFromAllGroups`）—— 只禁言一个群等于其余群完全没被处置。

两条轨道**共用同一张台账**，因此「cron 首次禁言过的号，之后在群里发言被消息路径抓到」也算第二次露头，会直接升级全群封禁 —— 这正是「再犯才升级」的本意。

**为什么首次是「禁言」而不是「封禁」**：`banChatMember` 会把人**踢出群**，而 `unbanChatMember` 只能解除封禁、**不会把人拉回群** —— 也就是说封禁的误判代价不可逆（人得自己重新进群），禁言的误判代价完全可逆（一条 `/ignore` 就恢复发言）。首次判定是整条链上**唯一可能出错**的一步（后面每一步都以「已被判定过一次」为前提），所以把不可逆的动作留到确认之后。禁言走 `restrictChatMember` + `use_independent_chat_permissions`，**永久**（不带 `until_date`），除「发送消息」外的权限一并撤销。

**首次判定的完整动作**：**消息触发** → 本群永久禁言 → 删掉触发那条消息 → **清扫该号在本群的近期缓存消息（上限 `AD_MUTE_CLEANUP_LIMIT` = 20 条）** → 写一行监控台账 → 通知第一主人。<br>**cron 主动扫描** → 所有治理群永久禁言 → 写一行监控台账 → 通知第一主人（**不做清扫**，理由见下）。**两条轨道都不写 D1 黑名单** —— 拉黑会让「黑名单兜底拦截」在他去别的群发言时删消息并封那个群，等于绕开「再犯才升级」直接做了近似全群封禁，渐进式就白做了。

**cron 轨道为什么不清扫消息**：它扫的是「资料卡就是广告」的号，**广告在简介里不在消息里**，没有触发消息可删；而逐群清扫会把子请求数乘上群数（4 群 × 20 条 = 80 次 `deleteMessage`），撞上 Workers 子请求上限会让整个请求抛异常 —— 处置明明生效却报错，比留几条历史消息糟得多。

**为什么首次必须自己补清扫**：`banChatMember` 的 `revoke_messages: true` 由 Telegram 服务端**一次撤回**该号在该群近 48 小时的全部消息（1 个子请求就够），而 `restrictChatMember` **没有这个能力**。不补这一步，首次命中就只删掉触发的那一条，前面几条广告会原样留在群里 —— 与「删消息范围跟随处置范围」的既有口径不符（`/ban` 群内路径、`/spam` 都是这么补的：从 `moderation_messages` 捞出该 TGID 在当前群缓存的消息 ID 逐条 `deleteMessage`）。<br>⚠️ 上限刻意比 `/ban` 的 `max(MSG_CACHE_SIZE, 200)` 小得多：`/ban` 是主人手工触发的低频路径，这里是**自动检测热路径**，逐条删除都是子请求，拿 200 去删会把子请求预算烧在善后上 —— 一旦撞上限整个请求抛异常，处置明明已经生效却因为清扫失败而报错，比留几条消息更糟。20 条足以覆盖「广告号连发几条」的真实形态，通知里会写明 `🧹 本群清扫 X/Y 条`；清扫失败只记日志，**绝不改变处置结果**。<br>**⚠️ 修复（2026-09-21）：清扫曾经「只删掉最后几条」**。根因**不在**这个 20 条上限，而在 `moderation_messages` 的**剪枝口径**：旧实现是全表 `ORDER BY id DESC LIMIT 1 OFFSET ?`，保留的是**所有群加起来**最新的 200 行。bot 在 N 个群时这个窗口被各群瓜分（4 个群时每群实际只剩约四分之一），B/C/D 群的正常发言会把 A 群广告号前面的消息一条条挤出缓存 —— 而清扫是**按 `mid` 查缓存**的，缓存里已经没有的 ID 就永远删不掉。线上实测形态：广告号连发 15 条，只清扫掉最后 5 条，前 10 条永远留在群里。<br>现已改为**按群剪枝**：每个群各自保留最近 `max(MSG_CACHE_SIZE, 200)` 行，剪枝时带 `WHERE chat_id = ?`，只动本群。一个群的缓存只被**本群**的新消息挤出，广告号连发的那一批必然完整。回归测试见 `test_ad_detection.mjs` 第 20.1c 节。

**首次没有黑名单兜底，所以禁言失败必须退回封禁**：这是不拉黑的代价。若 `restrictChatMember` 失败（权限不足 / 网络异常），会立刻降级 —— 消息触发轨道降级为**本群封禁**（回执标注 `📌 仅本群封禁（禁言失败降级）：`），cron 轨道**整体**降级为**全群封禁**（标注 `🌐 全群封禁：…（全群禁言失败：…，已退回全群封禁）`）。正常路径永远命中不到这两条分支。

**cron 轨道为什么整体降级而不是逐群降级**：这条轨道的语义就是「全群」，只降级成功的那些群会留下「部分群禁言、部分群封禁」的混合状态，更难解释也更难回滚。另外，`muteUserFromAllGroups` 会**先探测成员身份**，跳过「不在群内 / 已在群封禁列表」的群（那既不是禁言失败、也不该出现在失败群清单里），摘要的分母只算**实际尝试过**的群。

**升级的触发条件**：该号在**任意治理群**（`GROUP_ID` + `/addgroup` 动态群）**再次被判定为广告**即升级 —— 包括**同群再犯**（主人口径：任何第二次判定都视为惯犯，不再区分是不是同一个群）。注意触发条件是「**再次被判定为广告**」，不是「随便说句话」：他换个群发正常内容不会被升级。

**为什么升级走正常检测链而不是黑名单拦截**：首次不拉黑之后，该号不在黑名单里，他去别的群发言走的是**正常检测链** —— `detectAdOnMessage` → `decideAdBanScope` 读到台账 `scope_state='single'` → 返回 `reason='escalated'` → `enforceAdDetection` 执行全群封禁。函数 `maybeEscalateBlacklistedUser`（黑名单兜底拦截点）因此**不再是主要升级路径**，但仍保留：升级前就已拉黑的历史台账行、以及手工加黑后又产生台账的号，仍需要它来升级。

**哪些号不会被升级**：只有**广告自动判定**产生的封禁才有台账。手工 `/ban`、`/spam`、`/ad` 投票加黑的号没有台账记录，它们在群里冒泡**不会**触发升级 —— 那些号当初封禁时就已经走过全群封禁，没必要每次冒泡都重来一轮全群 API 风暴。

**台账被清掉的场景**（清掉后该号重新从「首次」开始）：
- `/ignore <序号>` 判误封回滚 → 同时删台账（否则一次误判会永久抬高该号后续的处置强度）
- 群内回复消息说「不是广告」→ 同样删台账
- `/unban` 人工解封（单条 / 批量）→ 删台账
- `/rescreen` 复查判定为干净 → 删台账

**哪些路径不受范围策略影响**（始终全群封禁）：
- **`/ad` 群内投票通过** —— 真人集体认定，且 `enforceApprovedAdVote` 是独立路径，本来就走全群封禁
- **`/rescreen` 批量复查** —— 主人手工发起的深度清理，与手工 `/ban` 同类；**手工动作一律不进渐进式**
- **`AD_BAN_SCOPE_MODE=global`** —— 一键回退旧行为

> **cron 定时 bio 复查（`runAdBioRescan`）曾经也在这张名单里，2026-09-19 移出。** 原先的理由是「它没有『当前群』语义，只封一个群等于主动扫描几乎不产生威慑」，于是直接全群封禁。但**「没有当前群」推不出「应该直接全群封禁」** —— 渐进式在这条轨道上有一个成立的等价物：禁言**所有治理群**（人全部留在群里、一条消息都发不出，不踢出不拉黑，误判可逆）。实测教训：cron 扫到一个资料卡广告号直接全群封禁，而主人认定那是误判 —— 一次误判把人在所有群里都踢了，代价不对称，正是渐进式要防的伤害。

**主群（联络通道）豁免自动处置**：**主群** = `SELF_UNBAN_CONTACT_GROUP`（留空时回落 `GROUP_ID` 的第一个群），它是这套系统里**唯一的对外联络通道**。自动判定（含禁言与封禁、黑名单兜底拦截、复入群拦截）**一律跳过它**：
- **为什么必须豁免**：被判定广告的号会进黑名单，而黑名单是自助解封的**硬闸门**（`blockSelfUnbanIfBlacklisted` 命中任何 reason 一律拒绝且不自动移出）。也就是说被全群封禁的号**既进不了群、也走不了自助解封** —— 如果连主群都被自动封掉，他就彻底没有任何途径联系到主人了。
- **为什么禁言也一起豁免**：只豁免封禁的话，误判者人虽然在主群里，却仍然**说不了话** —— 联络通道名义上开着、实际打不开，等于没豁免。豁免的粒度是「不处置这个人」，而不是「不把他踢出去」。
- **触发消息照删**：删消息是消息级动作，不改变任何人的成员状态，也就不会关上联络通道；不删的话主群就真成了广告可以随便刷的地方。清扫上限同样是 `AD_MUTE_CLEANUP_LIMIT` = 20 条。
- **豁免只给「自动判定」造成的黑名单**（`reason = ad_auto`）：手工 `/ban`、`/spam`、`/ad` 投票加黑是管理员的明确决定，**照常覆盖主群**，不会被悄悄削弱。
- **人工处置不受限**：`/ban`、`/spam`、`/ad` 投票、`/rescreen` 与判定通知里的「全群封禁」按钮一律照常覆盖主群 —— 它们也正是主群被刷广告时的出口。
- **台账照写**：豁免不改变台账语义（这次仍然算「已被判定过一次」），所以下次露头（无论在哪个群）`decideAdBanScope` 都会返回 `global` → 升级全群封禁（升级时同样跳过主群）。

**联络入口可以用「不依赖群身份」的链接**：环境变量 `SELF_UNBAN_CONTACT_URL`（例如**频道的私信链接**）会取代「去主群找人」，同时用于**自助解封成功回执**与**黑名单拒绝回执**。相比主群链接它有两个硬优势：① **不依赖群成员身份**，被全群封禁 + 拉黑的人照样点得到；② 主动来联系这个动作本身就是很强的反广告信号（广告号不会去申诉），所以这条通道可以放心开得很宽。留空则回落主群链接，与原行为完全一致；填了非法值（非 http/https）只打日志并回落，**绝不构造点不动的假按钮**。<br>⚠️ 黑名单拒绝回执原本只写「请自行联系管理员解封」而**没有任何联系方式** —— 被全群封禁的人进不去主群，等于彻底失联。现在这条回执一定自带联络按钮（+ 正文里的申诉指引）。

**通知下方带处置按钮**：判定通知的最后一块会挂两颗内联按钮 —— 左键是误判出口（禁言轨道显示 `✅ 解除禁言`、封禁轨道显示 `✅ 解除封禁`、主群豁免显示 `✅ 误判放行`），右键是 `🚫 全群封禁`。左键与 `/ignore <序号>` 走**同一个** `rollbackAdPendingSnapshot`（解禁 + 解封 + 指纹纠正 + 删错样本 + 清台账 + 登记放行库），只是入口从命令换成点击；右键是**人工路径**，因此**包含主群**。权限口径与 `/ignore`、`/words` 一致：**只认第一主人，且必须在他自己的私聊里点**（转发出去的通知点了不算）；回调数据里的 userId 与快照不一致时直接拒绝；处置完成后会摘掉键盘并标记快照已复核，重复点击不会重复处置。序号写在回调数据里，不存在敲错的可能。

**通知文案**：每次处置的主人通知里「处置结果」一行会写明动作与范围 —— `🔇 仅本群禁言：1/1 个群成功｜已进入监控，再次判定将升级全群封禁`（消息触发的首次）、`🔇 全群禁言（未踢出）：3/3 个群成功｜已进入监控，再次判定将升级全群封禁`（cron 轨道的首次）、`📌 仅本群封禁（禁言失败降级）：1/1 个群成功`（降级）、`🌐 全群封禁：3/3 个群成功`（升级后，分母不含被豁免的主群）或 `🏠 主群豁免（未处置）：未执行任何群处置｜已进入监控（主群豁免处置，如需立即处置请点下方「全群封禁」；再次判定将升级全群封禁）`（触发群正是主群）。首次路径若清扫到消息，会在中间多一段 `｜🧹 本群清扫 X/Y 条`（0 条时不写，避免每次塞废话）。首次判定的通知标题是 `🔇 广告号自动禁言（仅本群，未踢出）`（消息触发）、`🔇 广告号自动禁言（全群，未踢出）`（cron 轨道）或 `🏠 广告号判定（主群豁免，未处置）`（主群），与升级后的 `🚫 广告号自动封禁` 明确区分。升级时另发一条 `🚨 广告号升级为全群封禁` 通知，注明本次露头的群、首次处置的群、以及是「同群再犯」还是「换群投放」。

**误判怎么回滚**：`/ignore <序号>` 或**通知上的左键**会**解除该号在所有治理群的禁言**（`unmuteUserFromAllGroups`，覆盖全部配置群含主群 —— 解除禁言幂等且无副作用，人工回滚宁可多解不可漏解）→ 移出黑名单 → 全群解封 → 删指纹与 AI 样本 → 清台账 → 登记放行库。解禁必须覆盖全群，因为 cron 轨道的禁言本来就在多个群；只解触发群会留下「回执写着已解除禁言，而那个人仍在其余群说不了话」的假象。对没被禁言的人解除禁言是幂等的，且这条链紧接着就在跑全群解封，范围严格更大。<br>⚠️ 首次禁言的号**不在黑名单里**，所以 `/unban` 找不到他 —— 解除禁言只有 `/ignore`（序号在通知里）或通知按钮这一条路。

**D1 表**：`ad_ban_scope`（随广告检测那批表一并自动建立，无需手动建）。一行一人，字段含 `scope_state`（`single` / `global`）、`first_chat_id`、`first_chat_title`、`first_score`、`trigger_count`、`escalated_at` 等。它**不参与过期剪枝** —— 语义是「已被定过罪的账号」，只能由上面的回滚路径移除。<br>⚠️ `first_chat_id` **允许为空**：cron 轨道写台账时群号来自名册，历史数据可能没有。台账的语义是「这个号已经被判定过一次」，与「在哪个群」无关 —— 所以哪怕群号缺失也**必须**写这一行，否则该号永远是「首次判定」，升级链彻底断掉。

> **两个常见疑问**
>
> **只有一个治理群，还需要这个吗？** 不需要关心 —— 单群配置下 `progressive` 与 `global` 结果相同（「触发群」就是唯一的群），差别只在动作强弱：`progressive` 首次是禁言、`global` 首次就是封禁。
>
> **想「抓到一次就全网拉黑」怎么办？** 把 `AD_BAN_SCOPE_MODE` 填 `global`。这是多群场景下更简单直接的选择，代价是误封影响面更大（一次判定错就全群踢人）。默认给 `progressive` 是因为它把「一次判定」的爆炸半径压到了一个群、且首次动作可逆 —— 而 `/ignore` 一条命令就能回滚。

### 误判放行库

`/ignore` 原本只做「减法」：移出黑名单、全群解封、给误报指纹降权、删掉学错的 AI 样本。但**被误判的那条消息/昵称/简介本身仍然参与后续判定** —— 同一个人再发一次同样的内容，还是会照着同样的判据得同样的分，于是再被封一次。

**误判放行库（`ad_allowlist`）就是补这个「加法」**：`/ignore` 回滚的同时，把**本次判定真正读到过的素材**登记为「这是正常的」，此后这些素材**直接不参与判定**。

| 维度 | 登记内容 | 对应现场 |
| --- | --- | --- |
| `text` | 消息正文（归一化后） | 本人说的话被误判 |
| `name` | 显示名（`first_name` + `last_name` 拼接） | 昵称被误判 |
| `username` | `@用户名` | 用户名被误判 |
| `bio` | 个人简介 | 资料卡被误判 |

**粒度是「维度」而不是「整条消息」**：命中 `text` 只让**正文**退出判定，昵称 / 用户名 / 简介照旧参与。否则放行一条消息就等于给这个人发了免死金牌 —— 他改成广告昵称照样能被抓。反过来，如果只有昵称被放行，正文里的广告词仍然独立定罪。

**匹配方式：精确匹配**。存进去的是 `normalizeAdFingerprintValue` 归一化后的值（去零宽字符、空白折叠、trim、转小写、截 200），比较时逐字相等才算命中。刻意不做模糊匹配 —— 放行是**不可逆的减法**（放过一次广告），代价不对称，宁可漏放行让主人再 `/ignore` 一次，也不能因为「长得像」就把广告放过去。

**维度前缀防跨维度误放行**：放行键是 `维度:归一化值`（如 `text:xxx`）。昵称恰好等于某条被放行的正文时，不会因为正文被放行就连昵称一起放掉。

**只登记「确实参与过这次判定」的素材**：闸一（零成本判定）定罪时压根不拉资料，所以快照里的 `bio` 是空的，这条 `/ignore` 就只登记 3 项（正文 / 昵称 / `@用户名`），回执会如实写明登记了几项、是哪几项。

**永久有效 + 命中计数**：放行记录不设过期（`hit_count` 只统计被命中次数，用于日后识别长期零命中的残留）。放行素材必须是**完整归一化后长度 ≥ 2**，太短的（比如单字母正文）不入库 —— 那会退化成大面积放行。

**管理入口**：`/allowlist`（第一主人私聊）列出全部放行记录，按命中次数升序 —— **0 命中的排在最前面**，方便清理当初登记了但后来再没出现过的残留。`/allowlist del 序号 序号` 撤销某条（撤销后该素材立刻重新参与判定）。

**放行库不碰其他语义**：不删台账、不动黑名单、不动指纹库、不动 AI 样本 —— 它只影响「这一份素材参不参与判定」，与其他回滚动作互不干扰。

### 同款广告连带查杀

多个广告号刷同一段文案时，**第一主人**只需引用其中一条回复 `/spam`，系统会顺带把 24 小时内、全部配置群里的同款账号一并处置（删消息 + 加黑 + 全群封禁）。

**为什么以前做不到**：`moderation_messages` 原本只存 `mid` / `chat_id` / `from_id`，不存正文，所以只能对 `/spam` **之后**新发的消息生效，已经躺在群里的同款一条都追不到。现在新增 `text_hash`（FNV-1a 32 位）+ `text_norm`（归一化正文，截 200）两列，走哈希等值 + 时间窗口反查，一次 D1 查询跨群覆盖。

**存正文而非只存哈希的三个理由**：① 通知里展示原文，主人能一眼判断这条文案是否真是广告；② 拿到候选后二次比对兜住哈希碰撞（连带是批量不可逆操作，代价不对称）；③ 日后扩展「相似匹配」算编辑距离必须有原文。

**权限边界（最关键的安全属性）**：**仅 `OWNER_IDS[0]`（第一主人）可触发**。副主人 / 超级管理员 / 群管理员的 `/spam` 照常执行加黑 + 封禁 + 学指纹，**只是不连带**，且**完全静默**（不提示、不在群里留痕迹，不暴露这个能力的存在）。理由是连带的杀伤力是单次封禁的 N 倍，而误封的根源不是「代码判得不准」而是「谁有资格触发这个不可逆的批量操作」。

**判据只有一条**：第一主人 `/spam` 过就算 —— 长度门槛调过三轮（12 字 → 4 字 → 取消）每轮都被新样本打穿，因为广告文案可以短到任意长度。误封风险改由「仅第一主人可触发」+「一键回滚」两层兜住。仍然排除两种：空文案、斜杠命令（操作指令不是广告内容）。

**子请求预算**：本功能的硬约束。`telegramMutationAttempts = 2 × 号数 × 群数`，15 个群时每个号吃 30 个子请求。3 个号 ≈ 106（贴同步预算）、10 个号 ≈ 336、30 个号 ≈ 1047（撞 Cloudflare 单请求 1000 硬限）。因此：**单次硬上限 20 个号**，超出部分只列 TGID 供手动处理；**同步/批量分流按预算动态判断**（复用 `shouldUseBulkQueue`，与 `/ban` `/spam` 手动批量同一口径），超预算时转 D1 批量任务 + Queues 分片。

**批量路径为什么还要删同款消息**：`banChatMember` 的 `revoke_messages` 有两个硬限制 —— ① 只撤 48 小时内的消息；② 目标必须**仍在群里**（已退群 / 已被踢 / 账号已冻结的一条都撤不掉）。实测连带命中的号常显示「已注销用户 The account was frozen」，revoke 完全无效，消息原样留在群里。所以批量 payload 带 `deleteTargets`（精确到 mid，只删那几条同款、不是全部历史消息），执行时逐条 `deleteMessage`，**且不看封禁是否成功**（封禁失败常因 bot 无封禁权限，而删除权限独立，能删一条是一条）。

**通知**：处置完私聊第一主人，含操作人、触发群、源账号、同款文案原文、追溯范围、逐号处置明细，以及**一键回滚命令**（`/unban` 拼好的全部 TGID，可直接复制）—— 连带把单次误判乘以 N 倍，回滚入口必须现成。

### 逐字分隔混淆检测

广告号主流规避手法是在汉字间插分隔符躲词表匹配：`pq低.價.出.正.品.水.果.機 pp` —— 「低價出正品」被点号切碎，`includes` 全部失效。

**两个动作**：
- **A1 结构加分（打规避行为本身，不依赖任何广告词汇）**：正文命中混淆签名 +4 分，昵称 +3 分。广告内容可随意变，但只要还想躲词表匹配就必须用这个手法。
- **A2 去混淆文本参与词表匹配**：挂在 `countAdKeywordHits`（全项目唯一的词表匹配入口）上，一处改动即让结构化评分 / 指纹抽取 / 豁免词 / 引用体查杀全部覆盖混淆变体，无需为每种变体往词表加字面量。

**分隔符分两级（放宽分组后必须做的区分）**：
- **STRICT**（点号、间隔号、下划线、星号、破折号、波浪号、空白）：中文写作不用它们逐字断句，出现即混淆信号，允许 1~2 字分组
- **LOOSE**（顿号、逗号）：正规列举标点，只在**严格逐字**（每组恰好 1 字）时才算混淆

**为什么必须分级**：「苹果、香蕉、橘子、西瓜」「上海、北京、广州、深圳」这类中文列举天然是「2 字 + 分隔符」重复三次以上，只用一级会整片误伤。签名一律要求 **≥3 组连续**，且限定 CJK 字符类，避免英文缩写（`U.S.A`）与版本号（`1.2.3.4`）被误判。

**去混淆只在命中签名的片段内部剥分隔符**，签名之外的文本一个字符都不动 —— 否则「今日 入门」会拼成「今日入门」凭空命中「日入」。

### 回复学习触发词收紧

**线上事故复盘**：管理员在群里回复一句含「广告」二字的吐槽，把得分 -1（远低于阈值 7）的人封了 14 个群 —— 因为确认分支**强制 `verdict='ban'`，不受阈值裁决**，得分完全不参与决策。根因是 `AD_REPLY_LEARN_TRIGGERS` 配 `includes` 子串匹配，`'广告'` 会被「这广告真烦」命中，`'垃圾'` 会被「这游戏真垃圾」命中。现**一律要求带明确判定意图的完整短语**（`'这是广告'`、`'广告号'`、`'该封他'` …）。

**两张语义相反的词表已解耦**：
- `AD_REPLY_LEARN_TRIGGERS` = **封禁指令**，误触发即封错人 → 必须**严**，只认完整短语
- `AD_QUOTED_KILL_NEGATORS` = **举报者保护名单**（识别「引用广告 + 回一句『广告』警示他人」并放行），漏词即把举报者当广告号杀掉 → 必须**宽**，单词短语都收

原先后者写 `...AD_REPLY_LEARN_TRIGGERS` 展开复用，收紧触发词会连带打穿举报者保护，现独立维护、各自演进。

**另两项**：① 触发回复原文（截 60 字）写进 `reasons` 随快照进 D1，`/pending` 直接可见 —— 否则触发回复与被举报消息都被删除、群内零痕迹，排查只能翻 7 天就过期的 Cloudflare 日志；② **斜杠命令文本永不进指纹库**（整段正文兜底与短语截取两条路径同时过滤）—— 线上事故里 bot 无权限删不掉 `/ban` 命令消息，命令文本被当普通发言学成 `[keyword] /ban 1919451354`，权重 1 单条即定罪，构成「管理员用 `/ban` 封人 → 命令文本入库 → 下次发相同命令即被秒封」的自噬循环。

自动封禁**不是终点**。每次自动处置都会生成一条快照推给第一主人，1 小时内可复核：

| 命令 | 说明 |
| --- | --- |
| `/pending [N]` | 列出待确认的自动判定快照，默认 10 条。显示序号、TGID、得分、命中判据、现场资料（昵称/简介/正文）。快照保留 1 小时。 |
| ~~`/confirm 序号`~~ | **已于 2026-09-08 删除。** 定罪即自动学入指纹与 AI 语义样本，判定正确**无需任何操作**（回执里会写明这一行）。残留的 `/confirm` 字样只在本文档的历史说明里出现，代码里已无实现。 |
| `/ignore 序号` | **判定错误（误封）**：解除该号在**所有治理群**的禁言 + 移出黑名单（首次命中本就没拉黑，此时回执写「本就不在黑名单」）+ 遍历所有配置群解封 + 给所有命中该用户的指纹累加一次误报计数 + **把本次判定读到的素材登记进误判放行库**（见 [误判放行库](#误判放行库)）+ 清掉渐进式台账。累计 3 次误报且置信度跌破 0.2 的 auto 指纹**自动退役删除**。判定通知下方的左键与它**完全等价**。 |

| `/adstats` | 一屏总览：封禁/观察阈值、AI 绑定状态与模型名、指纹库规模与分类占比、Top 命中指纹、语义样本数、观察窗口人数、待确认快照数、域名白名单条数。**未绑 AI 时会明确写出「降级为评分 + 指纹两层」**，不会让你误以为三层都在跑。 |

### 指纹库与样本库维护（仅第一主人私聊）

| 命令 | 说明 |
| --- | --- |
| `/words [页码]` | 按命中次数倒序翻看指纹库，每页 20 条。显示类型、值、命中数、误报数、置信度、来源。 |
| `/addword 值 [类型]` | 手动新增指纹。类型可省略（`@xxx` → username，含 `.` 的合法域名 → domain，其余 → keyword）。手动指纹恒为 `weight=1`、`confidence=1`、`source=manual`，**永不被误报退役机制清除**。 |
| `/delword 值` | 删除指纹，按原文或归一化值匹配，跨类型一并清掉。 |
| `/addsample 文本` | 新增一条 AI 语义比对样本（至少 4 字）。向量留空，由 `/warmup`、`/adstats` 或后续检测懒加载补齐（每次最多 8 条，避免子请求超限）。 |
| `/warmup` | **补齐样本向量**，每次最多 8 条，反复发直到补满。<br>⚠️ **绑了 AI 但向量为 0 时，第三层实际是空转的** —— 向量原本只在第三层被调用时懒加载，而第三层需要「消息通过零成本预筛」才会触发；若指纹层已命中定罪更走不到第三层，于是新部署的向量可能长期停在 0。发几次 `/warmup` 即可补满，`/adstats` 也会顺带补一批并在回执里提示进度。 |
| `/clearsamples` | 清空全部语义样本，**需二次确认令牌** —— 第一次执行返回一个 16 位令牌，再发 `/clearsamples 令牌` 才真正清空。令牌一次性有效。 |
| `/whitelist [list\|add\|del] [域名]` | 域名白名单维护，白名单内的域名不计入链接可疑分。首次建表自动写入 50 条常用域名种子（github.com、gitlab.com 等）。支持 `*.example.com` 泛域名，子域名自动向上匹配父域。 |

> **指纹只做精确匹配**：归一化后完全相等（≥ 6 字）才单条定罪，**不做子串包含**。学了一条短广告词也绝不会炸到「碰巧含这几个字」的正常长消息。

### 阈值调优

五个可选环境变量，**建议先全部不填，用默认跑几天看 `/pending` 的复核结果再调**：

| 变量 | 默认 | 范围 | 调整方向 |
| --- | --- | --- | --- |
| `AD_SCORE_THRESHOLD` | `7` | 1~100 | 调低 = 更激进（漏放少但误封多）；调高 = 更保守 |
| `AD_OBSERVATION_SCORE` | `5` | 1~100 | 进观察窗口的门槛，应低于封禁阈值 |
| `AD_OBSERVATION_HOURS` | `24` | 1~720 | 观察窗口保留时长（小时） |
| `AD_AI_SIMILARITY_THRESHOLD` | `0.78` | 0.1~1 | AI 硬命中阈值，调低会显著增加误判 |
| `AD_FINGERPRINT_MIN_CONFIDENCE` | `0.6` | 0~1 | 低于此置信度的指纹不参与判定 |

> ⚠️ **别建空值变量**。在 Cloudflare 后台建了变量但值留空时，朴素的 `Number('')` 会得到 `0` —— 封禁阈值变成 0 就等于**所有人都被判广告**。代码里 `loadAdDetectionConfig` 已经先判空串再解析（空串、非数字、超范围一律回落默认值），所以不会真出事，但没必要留个空变量在那里。

### 运维建议

1. 部署后先私聊 bot 发 `/adstats`，确认「语义样本 共 10 条」「域名白名单 生效 50 条」—— 说明 11 张表和种子数据都建好了。
2. **绑了 AI 的话，接着发几次 `/warmup` 把向量补满**（每次 8 条）。`/adstats` 里「已生成向量」不为 0 才说明第三层真的在工作 —— 显示 0 时第三层等于不存在。
3. 前几天每天看一次 `/pending`。误封的用 `/ignore` 纠错（会自动给误报指纹降权），判对的**什么都不用做**（已自动学入指纹与 AI 样本）。
4. 遇到检测漏掉的广告号，回复它的消息说「这是广告」，或用 `/addword` 手工把特征加进指纹库。
5. 指纹库积累一批后用 `/rescreen` 回溯处理观察窗口里的人。
6. 觉得误封率偏高就调高 `AD_SCORE_THRESHOLD`；觉得漏放太多先补指纹，而不是急着调低阈值 —— 指纹库是精确匹配，比降阈值安全得多。
7. **别只看指纹库条数就以为检测很强**。结构化评分层单项判据大多 +2，单独很难凑够 7 分封禁线；真正定罪主要靠指纹层（+3，权重 ≥0.8 时单条即定罪）和 AI 层。指纹库空 + 向量为 0 的状态下，只有资料极其露骨的号会被封。

## 前置条件

- 一个 Telegram Bot Token，通过 [@BotFather](https://t.me/BotFather) 创建。
- 一个 Cloudflare 账号，启用 Workers。
- 本地安装 Node.js 和 Wrangler，或直接使用 Cloudflare 控制台部署。跑离线测试需要 **Node 22+**（`node:sqlite` 内置模块要求）。
- 机器人需要被加入目标群组并设为管理员。
- Workers AI **可选**：绑定后广告检测启用第三层语义判定；不绑自动降级为两层，其余功能不受影响。免费层每天有一定的 Neurons 额度，`bge-m3` 是轻量嵌入模型（不是大语言模型），正常群规模不会超限。

建议给机器人以下权限：

- 封禁用户或解除封禁
- 管理员权限或限制成员权限
- 读取群成员状态
- 发送消息

> `chat_member` 事件订阅要求机器人是群管理员，否则收不到该事件 — 但本来部署就要求管理员权限，无需额外配置。

>
> ⚡ **主群怎么定？** 主群 = `GROUP_ID` 的**第一个**群，固定规则，无需单独配置。二次审核提醒、解封联系入口默认都指向它。

### 必填（缺失会返回 500）

| 变量名 | 说明 |

### 可选（不填则使用源码顶部默认值）

| 变量名 | 默认 | 说明 |
| --- | --- | --- |

| `BLACKLIST_REASON_LABELS` | 见源码 | `/blacklist` 列表中"原因"字段的中文映射，**JSON 字符串**形式。例：`{"spam":"群内举报","manual":"管理员添加","manual_ban":"自动同步"}`。非法 JSON 时自动回退默认。 |

| `FLASH_MESSAGE_TTL_MS` | `5000` | **群内闪屏提示存活多少毫秒后自动撤回**（0~60000 的整数）。闪屏 = 群内执行授权命令后那条短提示，让操作者立刻看到结果又不长期污染群消息流。调大 = 看得更从容但残留更久；调小 = 群更干净但容易没看清就消失。<br>**填 `0` 表示永不撤回** —— 不推荐，闪屏回执常含 TGID 等不宜长期公开的信息。空串 / 非整数 / 负数 / 超过 60000 一律回落默认值。<br>⚠️ 只影响群内闪屏，不影响私聊详情（私聊消息永久保留）。`/help` 在群内的引导提示刻意固定为 6000ms，不随此项变化。 |
| `AD_SCORE_THRESHOLD` | `7` | 广告检测**封禁阈值**（1-100）。三层总分达到即加黑并按下方的封禁范围处置。调低更激进（误封增多），调高更保守（漏放增多）。 |
| `AD_BAN_SCOPE_MODE` | `progressive` | **广告自动判定的处置范围与动作**。`progressive`（默认）= **渐进式处置**：首次判定**只在触发判定的那个群禁言**（不踢出、不拉黑，人留在群里），同时把该号记入监控台账；该号此后在**任意治理群再次被判定为广告**（含同群再犯），才升级为**全群封禁**并标记「已升级」，不再重复升级。<br>`global` = 恢复旧行为，任何一层判定即**立即全群封禁**，不写台账。<br>取值只认这两个字面量（大小写不敏感），空串 / 非法值一律回落 `progressive` 并在 Worker 日志打一条警告。<br>**什么时候该填 `global`**：① 你只有一个治理群（此时两种模式等价）；② 出问题时用它一键回退旧行为。<br>⚠️ **渐进式的代价**：首次判定到升级之间存在时间窗口。该号若在**其他群**不再发广告（被禁言 / 只是潜水 / 只发正常内容），bot 就不会升级，也就只做了那个群的禁言。多群治理且希望「抓到一次就全网拉黑」的场景，建议直接用 `global`。 |
| `AD_OBSERVATION_SCORE` | `5` | 广告检测**观察阈值**（1-100）。总分达到但未及封禁阈值时进入观察窗口，不做任何处置，窗口内再发言分数累加。应低于封禁阈值。 |
| `AD_OBSERVATION_HOURS` | `24` | 观察窗口保留时长，单位小时（1-720）。 |
| `AD_AI_SIMILARITY_THRESHOLD` | `0.78` | AI 语义相似度**硬命中阈值**（0.1-1）。达到即直接定罪；落在 `[0.65, 该值)` 只加 2 分软加分。调低会显著增加误判。未绑定 AI 时此项无效。 |
| `AD_FINGERPRINT_MIN_CONFIDENCE` | `0.6` | 指纹参与判定的**最低置信度**（0-1）。置信度 = 命中数 / (命中数 + 误报数)，低于此值的指纹不参与判定但仍留在库里。 |
| `AD_PROTECTED_USERNAMES` | 空 | **权限人用户名永不学习白名单**。主人 / 副主人 / 超级管理员的 `@handle` 绝不允许进指纹库。逗号分隔（半角 `,` 与全角 `，` 都兼容），`@` 前缀可省，例 `ym94203,suqi_20` 或 `@ym94203，@suqi_20`。<br>只接受合规 Telegram 用户名（5-32 位字母数字下划线），过短 / 空值 / 含非法字符的一律丢弃 —— 防的是空串进列表后 `includes` 全量命中、等于关掉整个指纹层。<br>留空则只靠「username 只比对账号自身 handle」的结构性隔离兜底（已足够，本项是加固而非必需）。填上之后多一层保障：即使主人的 handle 被夹在某条 keyword 截断短语里，也不会入库。 |
| `STATIC_USER_PROFILES` | 空 | **`/admins` 权限名单的静态资料兜底**（JSON 字符串）。Telegram Bot API 只能查到 **bot 所在群**的成员资料 —— 主人 / 副主人 / 超级管理员若不在任何配置群里，`/admins` 只能显示 TGID，昵称与用户名都是「未获取」。<br>格式：`{"TGID":{"first_name":"昵称","username":"用户名"}}`，可含 `first_name` / `last_name` / `username`，`id` 由 key 自动补全，多个用户写成多个键。例：<br>`{"197282502":{"first_name":"威廉","username":"RealNeoMan"}}`<br>**只作兜底、不覆盖实时数据**：`resolvePermissionUserProfiles` 先用本表填充，再依次调 `getChatAdministrators` / `getChatMember`，API 查到就覆盖静态值。所以 bot 一旦和此人同群，显示的永远是 Telegram 实时资料，静态表自动让位。<br>key 必须是纯数字 TGID，非法 key 直接跳过；整段 JSON 解析失败时记一条错误日志并回落空表，不中断启动。 |
| `PROFILE_LOOKUP_GROUPS` | 空 | **只读资料群**：逗号分隔的群 ID（半角 `,` 与全角 `，` 均可），仅用于 `/admins` 查询用户昵称 / 用户名 / 来源群，**完全不参与治理**。<br>**什么时候用**：权限人不在任何 `GROUP_ID` 配置群里时，`/admins` 只能显示「未获取」。以往唯一解法是把那个群加进 `GROUP_ID`，但那等于**把封禁能力和命令权限一起开放**给一个本来只想借来查昵称的群。填在这里则：广告检测、封禁、`/ban` `/spam` 鉴权、`/purge`、`/ad` 投票**全都不会碰这些群**，该群的 Telegram 管理员不会因此获得任何权限。<br>**bot 在这些群不需要管理员权限**，普通成员即可（`getChatMember` 只要求 bot 在群内）。<br>只收 `-\d+` 形态（正数是用户 ID，传进 API 只会白报错）；已在 `GROUP_ID` 里的群自动剔除（那些群本来就会被遍历，重复只是多花请求）。<br>⚠️ 与 `STATIC_USER_PROFILES` 的区别：本项是**实时查询**（对方改昵称立刻反映），后者是**静态兜底**（写死值）。两者可同时使用，实时资料优先。 |

> ⚠️ **这 5 个 `AD_*` 变量建议一个都不填**，先用默认值跑几天，看 `/pending` 的复核结果再决定要不要调。调优思路见 [广告检测 → 阈值调优](#阈值调优)。
>
> **别建空值变量**：在后台建了变量但值留空，朴素的 `Number('')` 会得到 `0`，封禁阈值变 0 就等于所有人都被判广告。代码里已经先判空串再解析（空串 / 非数字 / 超范围一律回落默认值），不会真出事，但没必要留个空变量。

## 存储绑定

| 绑定 | binding 名 | 必需性 | 用途 |
| --- | --- | --- | --- |
| D1 Database | `DB` | **必需** | **唯一存储后端**。黑名单、清扫缓存、批量任务、投票状态、广告指纹库全部存 D1。表结构由代码自动建立，首次写入自动建表。 |
| Queue | `BULK_QUEUE` | 推荐 | `/ban` `/spam` `/unban` 超出同步安全预算后的自动续接队列。注意这是 Cloudflare Queue 绑定，不是 `wrangler secret put` 环境变量。 |
| Workers AI | `AI` | 可选 | 广告检测第三层语义判定（`@cf/baai/bge-m3` 1024 维多语言嵌入模型）。不绑则自动降级为「评分 + 指纹」两层。 |

> **未绑定 D1** 或 D1 黑名单读取失败时，自助解封会失败关闭并拒绝继续，避免绕过全局黑名单。`/ban` `/spam` `/unban` `/blacklist` 等命令会提示未绑定存储空间。
> **未绑定 `BULK_QUEUE`** 时，大批量任务仍会创建到 D1，但不会自动续接，需要管理员用 `/jobrun 任务ID` 手动补跑。
> **未绑定 `AI`** 时广告检测仍工作（评分 + 指纹两层），`/adstats` 会明确标注「未绑定，降级为评分 + 指纹两层」，不会静默失效。

### D1 表结构（全部自动建立，无需手动 SQL）

| 分组 | 表名 | 用途 |
| --- | --- | --- |
| 核心 | `schema_meta` | 核心 schema 版本号（当前 `6`） |
| 核心 | `blacklist` | 全局黑名单（TGID、原因、操作人、时间、备注） |
| 核心 | `moderation_messages` | 群内消息缓存，供 `/spam` `/ban` 清扫历史发言。**剪枝按群**：每个群各自保留最近 `max(MSG_CACHE_SIZE, 200)` 行，其他群的发言不会把本群缓存挤掉 |
| 核心 | `batch_jobs` | `/ban` `/spam` `/unban` 大批量任务状态与游标 |
| 核心 | `dynamic_groups` | `/addgroup` 指令添加的治理群组 |
| 投票 | `ad_votes` `ad_vote_allowlist` | `/ad` 投票状态（保留 7 天）与发起白名单。**按需建立** —— 首次用到 `/ad` 时才创建 |
| 广告检测 | `ad_fingerprints` | 广告指纹库（keyword / domain / username / bio 四类，含命中数、误报数、置信度、来源） |
| 广告检测 | `ad_user_screening` | 观察窗口记录（得分、判据、资料快照、过期时间） |
| 广告检测 | `ad_sample_embeddings` | AI 语义样本与向量（向量懒加载，首次建表写入 10 条种子） |
| 广告检测 | `ad_domain_whitelist` | 域名白名单（首次建表写入 50 条种子） |
| 广告检测 | `ad_exempt_keywords` | `/exempt` 维护的动态豁免关键词（与内置种子合并，只是减分不是放行） |
| 广告检测 | `ad_allowlist` | **误判放行库**：`/ignore` 登记的正常素材（正文 / 昵称 / `@用户名` / 简介），命中即退出判定 |
| 广告检测 | `ad_pending_snapshots` | 待确认快照，供 `/pending` `/ignore` 复核（序号长期保留，复核过的靠 `expires_at = 0` 从列表移除），保留 1 小时 |
| 广告检测 | `ad_confirm_tokens` | 二次确认令牌（`/clearsamples` 用） |
| 广告检测 | `ad_group_members` | 入群名册，记录每个号的最近发言群与 bio 复查时间（供 cron 回溯扫 bio） |
| 广告检测 | `ad_scan_state` | cron 扫描进度与每日配额计数 |
| 广告检测 | `ad_ban_scope` | **渐进式处置台账**：一行一人，记 `scope_state`（`single` / `global`）与首次处置群 |

> **广告检测的 11 张表走独立初始化路径**（张数以代码里的 `d1AdDetectionTablesExist` 清单为唯一真源），与核心表完全隔离 —— 老部署升级后现有黑名单数据**一条都不会动**。建表失败时整个广告层静默跳过并进入 60 秒冷却（避免 D1 抖动时每条消息都重试迁移耗尽子请求预算），既有功能不受任何影响。

## 部署

### 1. 安装 Wrangler

```bash
npm install -g wrangler
wrangler login
```

### 2. 创建 D1 数据库

```bash
wrangler d1 create tg-unban-bot-plus
```

把输出的 `database_id` 写到 `wrangler.toml` 的 D1 配置中（取消注释 `[[d1_databases]]` 段）。表结构由代码自动建立，无需手动执行 SQL。部署到新的 Cloudflare 账号时必须在新账号重新执行本命令，旧账号的 `database_id` 不能跨账号复用。

当前代码会自动创建以下 D1 表：

| 表名 | 用途 |
| --- | --- |
| `blacklist` | 全局黑名单，保存 TGID、写入来源、操作人和时间 |
| `batch_jobs` | `/ban` `/spam` `/unban` 自动创建的 D1 批量任务状态、进度、统计和失败记录 |
| `dynamic_groups` | `/addgroup` 指令添加的治理群组（与 `GROUP_ID` 环境变量分离存放） |
| `moderation_messages` | 配置群普通消息 ID 缓存，供 `/spam` 引用后清扫该用户近期消息。**按群剪枝**（每群各自保留最近 `max(MSG_CACHE_SIZE, 200)` 行）—— 这是「清扫不完整」修复的关键：全表共用窗口会让别的群把本群待清扫的消息挤出去 |
| `ad_votes` / `ad_vote_allowlist` | `/ad` 举报投票状态（带乐观锁 version）与发起白名单 |
| `schema_meta` | D1 结构版本号，用于跳过重复迁移 |

### 3. 创建批量任务 Queue

```bash
wrangler queues create tg-unban-bot-plus-bulk
```

`wrangler.toml` 已包含 `BULK_QUEUE` 的 producer / consumer 绑定。这里不需要新增环境变量，也不需要 `wrangler secret put BULK_QUEUE`。部署到新的 Cloudflare 账号时同样必须在新账号重新创建 Queue，并确认 `wrangler whoami` 显示的是目标付费账号。

### 4. 绑定 Workers AI（可选，广告检测第三层）

`wrangler.toml` 里已包含这段，用 `wrangler deploy` 部署会**自动生效**，无需手动操作：

```toml
[ai]
binding = "AI"
```

如果你是在 **Cloudflare Dashboard 里直接粘贴代码**部署（不走 wrangler），需要手动加：
**你的 Worker → 设置 → 绑定 → 添加绑定 → Workers AI → 变量名填 `AI`**。

不绑也能跑：广告检测自动降级为「评分 + 指纹」两层，`/adstats` 会标注降级状态。其余所有功能完全不受影响。

> AI 只在**通过零成本预筛的可疑消息**上调用，正常聊天不会触发。用的是轻量嵌入模型 `@cf/baai/bge-m3`，不是大语言模型，单次调用消耗很小（$0.012/M tokens）。样本库向量还有懒加载（每请求最多补 8 条）与运行期缓存，正常群规模不会撞免费额度。

### 5. 启用 Observability（可选）

参考 `wrangler.toml` 中的 `[observability]` 配置段。建议至少开启 `logs`，因为 Worker 会输出 Telegram 更新、权限检查、API 返回、广告判定得分与判据等调试信息。

广告检测的日志前缀是 `[广告检测]`，机器人风控是 `[机器人风控]`，投票是 `[/ad]` —— 在 Workers Logs 里按前缀过滤即可定位。

### 6. 设置环境变量

#### 6.1 最小可用配置（3 个必填项）

只填这三个就能跑起来。**在 Cloudflare Dashboard → 你的 Worker → 设置 → 变量和机密 → 添加**，或用命令行：

```bash
wrangler secret put TOKEN        # 输入：一串你自己定的随机字符串，用作 HTTP 接口密码
wrangler secret put BOT_TOKEN    # 输入：BotFather 给的 token
wrangler secret put GROUP_ID     # 输入：-1001234567890
```

具体填什么值：

| 变量 | 填什么 | 示例值 | 从哪来 |
| --- | --- | --- | --- |
| `TOKEN` | 你自己编的随机字符串（当 HTTP 接口密码用，越长越好） | `k7Xm9pQ2vR8nL4wZ` | 自己想一个，或用密码生成器 |
| `BOT_TOKEN` | Telegram Bot Token | `7123456789:AAH1x-yZabcdefGHIJklmnOPqrsTUVwxyz` | Telegram 找 [@BotFather](https://t.me/BotFather) → `/newbot` |
| `GROUP_ID` | 群组 ID，**多个用逗号分隔**，**第一个是主群** | 单群：`-1001234567890`<br>多群：`-1001234567890,-1009876543210` | 见下方「怎么拿群组 ID」 |

> **怎么拿群组 ID**：把 bot 拉进群并设为管理员，群里随便发一句话，然后打开 Cloudflare Workers Logs，日志里会打印 `聊天ID: -100xxxxxxxxxx`。也可以把 [@getidsbot](https://t.me/getidsbot) 拉进群用 `/id`。**超级群组 ID 一定是 `-100` 开头**。

#### 6.2 推荐加上（强烈建议）

| 变量 | 填什么 | 示例值 | 不填的后果 |
| --- | --- | --- | --- |
| `OWNER_IDS` | 你自己的 TGID。**第一个是主人**，后面是副主人，逗号分隔 | 单人：`123456789`<br>多人：`123456789,987654321` | 收不到任何私聊通知，所有隐藏指令全部不可用 |

> **怎么拿自己的 TGID**：私聊 [@userinfobot](https://t.me/userinfobot) 发任意消息，它会回你的 ID。
> **必须先私聊过 bot 一次**（发个 `/start`），否则 bot 无法给你发私信，通知会投递失败。

#### 6.3 自助解封文案与主群（可选）

| 变量 | 填什么 | 示例值 | 不填的后果 |
| --- | --- | --- | --- |
| `SELF_UNBAN_CONTACT_GROUP` | 解封成功后「联系管理员」按钮指向哪个群。**必须是 `GROUP_ID` 里已有的群** | `-1001234567890` | 用 `GROUP_ID` 的**第一个群**（即主群），大多数人不需要填 |
| `SELF_UNBAN_CONTACT_URL` | 联络入口链接，**优先级高于上一行**。推荐填**频道私信链接** | `https://t.me/yourchannel?direct` | 空（回落主群链接） |
| `SELF_UNBAN_KEYWORD` | 用户必须逐字粘贴的确认句 | `我不是广告狗，我是误封的，希望可以解封。` | 用内置默认句 |
| `SELF_UNBAN_APPROVED` | 解封成功文案（**能拿到群链接时用**） | 见 6.6 完整示例 | 用内置默认文案 |
| `SELF_UNBAN_APPROVED_NOLINK` | 解封成功文案（**拿不到群链接时的降级版**） | 见 6.6 完整示例 | 用内置默认文案 |

> **主群怎么设？** 主群 = `GROUP_ID` 的**第一个**群，这是固定规则，不需要单独配置。
> `SELF_UNBAN_CONTACT_GROUP` 只在你希望「联系入口」指向**非第一个**群时才需要填。
> 例：`GROUP_ID = -1001111,-1002222`，主群是 `-1001111`；若你想让解封用户去 `-1002222` 找你，就填 `SELF_UNBAN_CONTACT_GROUP = -1002222`。

#### 6.4 其它可选项

| 变量 | 示例值 | 说明 |
| --- | --- | --- |
| `SUPER_ADMINS` | `123456789,987654321` | 超级管理员 TGID，逗号分隔。可跨群使用管理命令 |
| `BLACKLIST_PAGE_LIMIT` | `30` | `/blacklist` 单次展示条数，正整数 |

#### 6.5 广告检测阈值（可选，**建议一个都不填**）

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `AD_SCORE_THRESHOLD` | `7` | 封禁阈值（1-100） |
| `AD_BAN_SCOPE_MODE` | `progressive` | 处置范围与动作。`progressive` = 首次**禁言**（不踢出不拉黑；消息触发只禁言触发群，cron 主动扫描禁言所有治理群）、再犯才全群封禁；`global` = 一次判定即全群封禁（旧行为） |
| `AD_OBSERVATION_SCORE` | `5` | 观察阈值（1-100），应低于封禁阈值 |
| `AD_OBSERVATION_HOURS` | `24` | 观察窗口小时数（1-720） |
| `AD_AI_SIMILARITY_THRESHOLD` | `0.78` | AI 相似度硬命中阈值（0.1-1） |
| `AD_FINGERPRINT_MIN_CONFIDENCE` | `0.6` | 指纹最低参与置信度（0-1） |

> 默认值是按真实广告样本调过的。**先用默认跑几天，看 `/pending` 的复核结果再决定要不要调** —— 凭感觉调阈值不如往指纹库里加几条精确指纹。详见 [广告检测 → 阈值调优](#阈值调优)。
>
> ⚠️ 别在后台建这些变量却留空值。

## 使用方法

### 用户自助解封

1. 用户私聊机器人发送 `/start` 或 `/unban`。
2. 机器人返回自助解封说明，包含一段 `<code>` 提示语供复制。
3. 用户**完整复制粘贴**以下整句（多/少标点、夹带任何字符均会被拒绝）：

   ```text
   我不是广告狗，我是误封的，希望可以解封。
   ```

4. 机器人遍历每个配置群，检查用户在该群的状态：
   - `kicked` → `unbanChatMember` 解封
   - `restricted` 或发言权被关闭 → `restrictChatMember` 恢复发言
   - 已是正常成员 → 提示无明显限制
5. 全部群处理完后返回逐群结果。
6. 若用户存在 GKY 封禁记录，会在主群 @管理员 并附上 `/start check_用户ID` 二次审核深链；管理员打开深链后，机器人在私聊返回双库查询结果和相应的纯复制按钮。

### 二次审核流程

管理员主动使用 `/check`，或打开自助解封提醒中的 `/start check_用户ID` 深链后，查询结果底部会根据双库状态显示 0～2 个复制按钮：

- **📋 点击复制 GKY 添加白名单代码**：仅当 GKY 封禁记录属于 `GROUP_ID` 配置群时显示，复制内容精确为两行 `GKYbotSave\n用户ID`。复制后必须由真人管理员在封禁记录对应的群发送。
- **📋 点击复制 本地解封命令**：仅当用户在本地 D1 黑名单时显示，复制内容为 `/unban 用户ID`。复制不会直接修改 D1，仍需由有权限的管理员发送执行。

两套状态相互独立：两边都封禁时显示两个按钮；只有一边封禁时只显示对应按钮。机器人不会自动发送或执行这些命令。<br>GKY 记录来自别的群时**照样给按钮**，只是语义变为「加 GKY 全局白名单」并附风险提示。<br>两种情况不给 GKY 按钮：GKY 返回记录的 TGID 与查询目标核对不上；或查询来自非 `GROUP_ID` 群（此时任何按钮都不给）。

## 常见问题

### Q1：访问 `/{TOKEN}` 返回 500，或部署后 Webhook 不工作

**原因**：环境变量 `TOKEN` / `BOT_TOKEN` / `GROUP_ID` 三项缺一不可，缺失会直接返回 500。
**解决**：

1. 用 `wrangler secret list` 或在 Cloudflare Dashboard 检查三项变量是否都填了。
2. `TOKEN` 不是 Telegram Bot Token，而是你自定义的初始化入口密钥（建议随机长字符串）。
3. `BOT_TOKEN` 才是 [@BotFather](https://t.me/BotFather) 给的 Token。
4. `GROUP_ID` 必须是机器人所在的目标群组 ID（负数，例如 `-1001234567890`）。

### Q2：用户在私聊发了正确确认句却没被解封

**原因**：本项目要求**完整逐字粘贴**才放行，多/少标点、夹带任何字符都会被拒绝（用于阻止广告号绕过）。
**解决**：

1. 用户必须直接复制 `<code>` 标签里的整句，不能手打。
2. 若你修改了 `SELF_UNBAN_KEYWORD`，欢迎语里的 `<code>` 提示语会自动同步，但用户必须用**当前生效的整句**，不是旧的。
3. 检查用户是否在 D1 全局黑名单（这是永久封禁，第一道闸就被拦下，必须由管理员手动 `/unban` 才能解除）。

### Q3：机器人收不到群里管理员手动封/解封的同步信号

**原因**：`chat_member` 事件需要机器人**本身是群管理员**才能收到。
**解决**：

1. 把机器人设为目标群组的管理员。
2. 重新访问 `https://你的Worker域名/{TOKEN}` 让机器人重新订阅 webhook。
3. 检查 Cloudflare Worker 日志：每次有 `chat_member` 事件时会打印 `[chat_member] 群内手动封禁，按规则不同步加黑` 或 `[chat_member] 拦截群内手动解封(D1黑名单保护)` 日志。

### Q4：为什么点击复制后 GKY 不会自动处理

**原因**：`copy_text` 按钮只把命令复制到剪贴板，不会以机器人或当前用户身份自动发送。实测 GKY 不处理其它 Bot 代发的 `GKYbotSave`，因此本项目已删除自动代发链路。
**解决**：

1. 点击「📋 点击复制 GKY 添加白名单代码」。
2. 由真人管理员把复制出的两行 `GKYbotSave\n用户ID` 粘贴到封禁记录对应的 `GROUP_ID` 配置群并发送。
3. 如果 GKY 封禁记录来自别的群，按钮会变成「GKY 添加全局白名单代码」—— 发出后该号在所有接入 GKYbot 的群都被放行，确认无误再发。
4. 本地 D1 黑名单是另一套状态，需要复制并执行 `/unban 用户ID`，GKY 白名单不会自动清除本地记录。

### Q5：D1 绑定后黑名单或批量任务为空

**原因**：本项目只读取 D1。D1 表结构会由代码自动创建，但已有数据必须已经写入对应 D1 表。新部署后如果还没有创建过 `/ban` `/spam` `/unban` D1 批量任务，`batch_jobs` 没有任务数据属于正常情况。
**解决**：确认 `wrangler.toml` 或 Cloudflare Dashboard 已绑定 `DB`，并检查 D1 中的 `blacklist`、`batch_jobs`、`moderation_messages`、`dynamic_groups` 表数据是否存在。绑定正确后无需额外接口，重新部署或重新访问 bot 即可使用 D1 数据。

### Q6：`/banlist?tgid=...` 返回失败或无数据

**原因**：`/banlist` 依赖外部服务 `https://gkybot.gmeow.cc/banlist`，外部不可用时查询会失败。
**解决**：

1. 等外部服务恢复，或换一个 GKY 兼容的后端：设置 `GKY_BANLIST_ENDPOINT` 环境变量。
2. 注意：如果换后端，新后端返回的 HTML 必须与 `parseBanlistHTML` 的正则匹配，否则即使联通也解析不出。

### Q7：修改了 `_worker.js` 顶部的 `DEFAULT_*` 默认值，但没生效

**原因**：环境变量优先级高于顶部硬编码。如果 Cloudflare 后台已经填了同名环境变量，会覆盖你改的源码。
**解决**：

1. 检查 Cloudflare Dashboard 是否填了同名环境变量。
2. 如果填了，要么删掉环境变量、要么直接修改环境变量的值（环境变量更方便）。
3. 修改源码后必须 `wrangler deploy` 重新部署才生效。

### Q8：管理员命令（`/ban` `/spam` `/check` `/blacklist`）没反应

**原因**：管理员鉴权策略是「调用者必须是任一配置群（GROUP_ID 列表中的任意一个）的管理员」。
**解决**：

1. 确认你是 `GROUP_ID` 中至少一个群的管理员或群主。
2. `/ban` `/unban` 可私聊或群内发送；`/blacklist` 需要私聊机器人发送。
3. `/spam` 可回复消息发送，也可直接 `/spam 用户ID`；回复消息时会额外删除被回复的垃圾消息，回复后面的文本会作为执行原因。
4. `/check` 有两种用法:群内**回复某条消息**发 `/check`;**或 `/check TGID`**(私聊或群内均可,如 `/check 993005028`)。私聊发不带参数的 `/check` 会提示正确用法。
5. `/job 任务ID [页码]` 用于查询 `/ban` `/spam` `/unban` 自动创建的 D1 批量任务；正常情况下任务会自动分阶段续接到完成，`/jobrun 任务ID` 仅用于异常中断后的手动补跑。
6. 检查 Worker 日志中的「权限状态: xxx」行，能看到机器人查到的你当前角色。

### Q9：部署后环境变量被意外重置

**原因**：默认情况下 `wrangler deploy` 会用本地 `wrangler.toml` 覆盖远端配置。
**解决**：本项目 `wrangler.toml` 里已设置 `keep_vars = true`，部署时会保留 Cloudflare Dashboard 中已有的环境变量。如果你 fork 后改了这个配置，记得改回来。

### Q10：自助解封通过后，用户为什么还是不能在群里发言

**原因**：本机器人解封流程只调用 Telegram 的 `unbanChatMember` / `restrictChatMember`，恢复账号在群里的「能否发言」状态。但有些场景仍可能受限：

1. 用户没重新加入群组（`kicked` 状态解封后用户需要重新点链接加群）。
2. 用户被其它机器人/反垃圾系统单独标记限言（与本机器人无关）。
3. 用户在 GKY 全局黑名单中 — 这种情况会触发主群二次审核提醒，需要管理员处理 GKY 那边的封禁。
4. 用户在 D1 本项目的全局黑名单中 — 这个永远拦在第一道闸，必须管理员 `/unban` 才能放行。

### Q11：`/ban` `/spam` `/unban` 批量超过 50 个怎么办

**原因**：三条命令单次输入都受 `_worker.js` 的 `BATCH_LIMIT = 50` 限制。每个不超过 50 人的批次会统一计算请求预算：只有 `U < 20`、`U × G <= 24` 且预计子请求 `<= 100` 时同步执行，其余情况自动创建 D1 批量任务。
**解决**：

1. 超过 50 个 TGID 时，把 `/ban`、`/spam` 或 `/unban` 都拆成每批最多 50 个再发送。
2. 每个批次可以直接粘贴，例如 `/ban [100,101,102,...]`、`/spam 100,101,102,... 批量广告`、`/unban [100,101,102,...]`。达到 Queue 条件后会保存到 `batch_jobs`，D1 每批最多处理 20 人，每轮最多执行 24 个“用户 × 群组”操作，并发硬上限为 3。
3. Queue 执行阶段不查询姓名；任务完成后只有主人查看 `/job 任务ID [页码]` 时，才会按每页最多 10 人按需查询资料。
4. 任务创建后会返回任务 ID。正常情况下 Queue 会自动续接；若 Queue 未绑定或自动续接被外部异常打断，可用 `/jobrun 任务ID` 补跑。
5. 分隔符可混用：半角 `,` / 全角 `，` / 空格 / 换行，也支持 `[123,456]` 数组外壳。重复 ID 会自动去重，单个用户失败不会让整批停止。

### Q12：`/{TOKEN}/export` 接口怎么用，安不安全

**原因**：原项目没有导出接口，本项目新增 `GET /{TOKEN}/export`，支持浏览器查看 / JSON 下载 / CSV 下载（Excel 友好）。
**安全性**：

1. 受 `TOKEN` 保护，URL 必须带正确 TOKEN，否则路由不匹配返回 405。
2. 所有用户输入字段（TGID / 原因 / 操作人 / 时间）通过 `escapeHtml` 转义，HTML 视图无注入风险。
3. `Cache-Control: no-store` 头确保中间代理不会缓存敏感数据。

**使用方式**：

| 场景 | URL |
| --- | --- |
| 浏览器查看（带搜索过滤） | `/{TOKEN}/export` |
| 下载 JSON 备份 | `/{TOKEN}/export?format=json` |
| 下载 CSV 给 Excel | `/{TOKEN}/export?format=csv` |

**注意**：

1. TOKEN 不要泄漏（同时也是 webhook 初始化密钥），泄漏即等于黑名单可被任何人查看下载。
2. 导出量不受 `BLACKLIST_PAGE_LIMIT` 限制 — 那是 `/blacklist` 命令的展示上限，导出永远全量返回。

### Q13：`/ban` `/spam` 显示"全部群踢人失败"怎么办

**原因**：踢人需要 bot 在目标群拥有"封禁用户"权限。bot 不是群管理员，或者管理员权限里关闭了"封禁用户"开关时，Telegram 会拒绝 `banChatMember` 请求。
**解决**：

1. 进入目标群组 → 群设置 → 管理员 → 找到本机器人 → 打开"封禁用户"权限。
2. 确认开关：**封禁用户（Ban Users）**、**删除消息（Delete Messages）** 这两项必须打开。
3. 改完后无需重启 Worker，下次触发 `/ban` `/spam` 立即生效。
4. 如果想清扫之前因权限不足"加黑了但没踢"的存量用户：浏览器访问 `https://你的Worker域名/{TOKEN}/purge/run` 自动分批扫描清扫。

### Q14：黑名单用户的旧消息怎么办，会被自动删吗

**原因**：本项目调用的 `banChatMember` API 带 `revoke_messages: true`，Telegram 会**自动撤回该用户最近 48 小时**内在该群发的所有消息。这是 Telegram 平台规则，48 小时之外的消息**无法撤回**。
**解决**：

1. 自动撤回 48 小时内消息已是 Telegram 上限，本项目无法做更多。
2. 如需删除更早的消息，只能群管理员手动逐条删，或群管理员用 Telegram 客户端的"清除全部消息"功能（针对单个用户）。
3. `/spam` 命令额外删除被回复那条具体的垃圾消息，不受 48 小时限制（因为是按 `message_id` 直接删）。
4. **`/spam` 三种用法(引用回复 / `/spam 123` / `/spam 123 原因`)现已统一开启 `revoke_messages: true`**：加黑封禁的同时，Telegram 会自动撤回该用户在**所有配置群**近 48 小时内发的全部消息，无需再逐条手动删（旧版引用回复模式曾误设 `revoke_messages: false`，只删被回复那一条，靠缓存补删又存不全历史消息，已修复）。缓存清扫作为兜底，补删 revoke 偶尔漏掉的当前群近期消息。加黑命令 `/ban` 走同一套封禁逻辑，行为一致。

### Q15：群里发了 /ban 或 /spam 但没收到私聊详情

**原因**：本项目 `/ban` `/spam` `/unban` 在群内执行时，机器人会先发 5 秒闪屏；私聊详情按 `OWNER_IDS` 通知规则投递。Telegram 平台规则：**bot 不能主动给从未交互过的用户发私信**。如果主人/副主人从未私聊过这个机器人，私聊投递会失败；如果没有配置 `OWNER_IDS`，群内场景只保留闪屏。
**解决**：

1. 主人/副主人分别私聊机器人发一次 `/start`（或任意消息）即可建立会话，之后机器人就能给对应账号发私信。
2. 检查 `OWNER_IDS` 是否正确配置；第一个是主人，后续是副主人。
3. 群内授权指令除 `/check` 外会撤回命令消息本身；普通用户无权限命令不会被撤回，也不会执行。
4. 如果只想看到私聊详情、不想群里有任何痕迹，依然可以**直接私聊机器人发 `/ban` `/spam` `/unban`**（向后完全兼容，行为不变）。

### Q16：群里 /ban 闪屏 5 秒自动撤回，但闪屏没消失

**原因**：闪屏自动撤回靠 `deleteMessage` API，bot 必须有"删除消息"权限。如果 bot 不是群管理员或权限不足，闪屏会留在群里不撤回。
**解决**：

1. 进入目标群组 → 群设置 → 管理员 → 找到本机器人 → 打开"删除消息"权限。
2. 主流程不受影响：加黑、踢人、私聊详情都已经完成，只是闪屏没自动撤回。
3. 群管理员可以手动删那条闪屏消息。

### Q17：群管理员 / 其他超管在群里发命令，他们自己收不到私聊详情

**原因**：本项目设计了"主人/副主人审计通知"机制 — 一旦配置 `OWNER_IDS`，群内命令详情不再发给每个触发管理员，而是按固定规则投递：
- `OWNER_IDS[0]` 是主人，收到全部通知
- `OWNER_IDS[1..]` 是副主人，只收到 `/ban`、`/spam` 的加黑踢出通知
- 其他管理员/超管在群里看到闪屏知道执行结果即可，不接收私聊详情
- `/ban` `/spam` 通知详情会包含命令来源、作用范围、执行原因；群内执行会显示具体群名和群 ID，私聊执行会显示来源为私聊

如果你希望恢复"每个管理员各自收到自己的详情"老行为：
- 不配置 `OWNER_IDS`(留空) → 退化为只发群闪屏，不发任何私聊详情(简化模式)
- 想要"每个人都收自己的"老行为，本项目当前不支持。如果你需要，可以提 issue 提议加 `BROADCAST_TO_TRIGGER` 开关

### Q18：配置了 OWNER_IDS 但主人/副主人收不到通知

**原因**:Telegram 平台规则 — bot **不能主动给从未交互过的用户发私信**。如果你设了 OWNER_IDS 但对应账号从未私聊过 bot，通知投递会失败。

**解决**：

1. 主人/副主人账号分别私聊 bot 发一次 `/start`（任意消息都行），建立会话
2. Worker 日志会显示 `[审计通知] 私聊主人...失败:Forbidden: bot can't initiate conversation` — 凡是看到这条日志，就是该账号没建立私聊
3. 检查 OWNER_IDS 是否填了**正确的纯数字 TGID**（不要填 username）
4. 临时禁用通知 → 把 OWNER_IDS 留空，Worker 自动退化

### Q19：操作人标签会显示"主人"/"超级管理员"/"群管理员"，怎么判断

**原因**：本项目按以下优先级判定操作人角色（用于审计通知标签）：

1. 如果操作人 TGID **等于 `OWNER_IDS[0]`** → 标"主人"
2. 如果操作人 TGID 在 `OWNER_IDS[1..]` → 标"副主人"
3. 否则如果在 SUPER_ADMINS 名单 → 标"超级管理员"
4. 否则按调用上下文兜底（chat_member 同步标"群管理员"，命令鉴权后默认"管理员"）

**示例**：

- 你自己(主人) `/ban 123` → 私聊收到"🔔 主人操作通知"
- 副主人 `/spam` 或 `/ban 123` → 主人和副主人收到加黑踢出通知
- 名单中的超管 X `/ban 123` → 主人收到"🔔 超级管理员操作通知\n操作人:X(超级管理员)"
- 群管理员 Y `/ban 123` → 主人收到"🔔 群管理员操作通知\n操作人:Y(群管理员)"

### Q20：隐藏指令对其他人真的完全无反应吗

**是的,这是有意设计**。OWNER_IDS 专属隐藏命令的鉴权规则:

1. **一般隐藏指令只有 `OWNER_IDS` 中的主人/副主人能用**。`/admins` 更敏感,只允许 `OWNER_IDS[0]` 主人私聊使用。
2. **非主人在群内**:完全静默,连"权限不足"都不回,避免暴露命令存在。
3. **非主人在私聊**:回"权限不足",但**不泄漏命令的具体功能**(`/help` 对非主人也只回权限不足,不展开清单)。
4. **不注册到命令菜单**:这些命令不在 `setMyCommands` 里(只注册了 `/unban` `/ban` `/spam` `/check` `/blacklist`),所以用户在 Telegram 输入框敲 `/` 看不到它们,天然隐藏。
5. 主人想随时查看全部隐藏指令:**私聊**发 `/help`;想查看当前主人/副主人/超级管理员名单:**私聊**发 `/admins`。

### Q21：管理员置顶消息后，置顶被 bot 删除并取消了

**已在 v2 修复**。如果你还在旧版本，升级后需要额外清一次存量缓存。

**根因**：Telegram 在有人置顶消息时会推送一条 `pinned_message` **服务消息**，它的 `from` 是置顶操作者、`message_id` 是这条服务消息自身。旧版清扫缓存的入库条件只排除了机器人和斜杠命令，而服务消息没有 `text` 字段，因此照样被写进 `moderation_messages`。之后该用户一旦被 `/spam` 引用清扫或 `/ad` 投票通过，清扫逻辑就会删掉这条服务消息 —— 而**删除 `pinned_message` 服务消息，Telegram 的表现正是「取消置顶」**。频道关联群里「Channel 置顶了信息」被删也是同一原因。

**修复内容**：新增服务消息识别（覆盖置顶、入群/退群、改群名、话题、视频通话、支付等 28 类），在三处排除：① 清扫缓存入库（调用点 + 函数内双保险）；② 广告自动检测入口（否则置顶一条含广告词的消息会让**置顶者**被当成广告发布者加黑）；③ `/recent` 学习候选。

**投票置顶不受影响**：本项目的 `pin`/`unpin` 只对 bot 自己发出的投票卡片操作（3 个调用点全部带 `state.messageId`），投票发起时置顶、通过/否决/到期/取消时取消置顶，绝不碰群里其它置顶。

**升级后必做**：旧版已经把一批置顶服务消息 ID 写进了 D1，不清掉的话它们在下次清扫时仍会被删一次，你会误以为修复没生效。在 Cloudflare D1 控制台执行：

```sql
DELETE FROM moderation_messages;
```

该表仅为清扫缓存（记录"某用户在某群发过哪些消息 ID"，供 `/spam` 引用清扫用），清空**不影响**黑名单与投票数据。

### Q22：Windows 下 `git push` 报 `ServicePointManager 不支持具有 socks5 方案的代理`

这不是本项目的问题，但用 v2rayN / Clash 等代理推送本仓库时很常见，记录在此。

**原因**：Git Credential Manager 是 .NET 程序，其 `ServicePointManager` **只支持 `http://` 方案的代理，不支持 `socks5://`**。若把 git 代理配成 socks5，GCM 无法完成浏览器授权，会退化成密码认证，而 GitHub 已停用密码认证，最终报 `Password authentication is not supported`。

**解决**：把 git 代理改成 `http://` 方案。v2rayN 的 SOCKS 端口（默认 10808）在新版本通常也接受 HTTP CONNECT，可直接复用：

```bash
git config --global http.proxy  http://127.0.0.1:10808
git config --global https.proxy http://127.0.0.1:10808
```

若不生效，在 v2rayN「设置 → 参数设置」里确认 `本地http端口`（默认 10809）已启用，然后改用该端口。验证连通：

```bash
git ls-remote origin        # 能列出 refs 即代理可用
```

**另外两个 Windows 常见坑**：

- `fatal: detected dubious ownership` —— 仓库目录所有者 SID 与当前用户不一致（拷盘/换用户后常见）。执行 `git config --global --add safe.directory <仓库绝对路径>`。
- Git Bash 里粘贴出现 `bash: $'\E[200~git': command not found` —— 这是「括号粘贴」控制字符被当成命令名。改用**右键 → Paste** 或 **Shift+Insert**，或执行 `echo 'set enable-bracketed-paste off' >> ~/.inputrc` 后重开终端。

### Q23：频道置顶的内容在关联讨论群被 bot 删除并取消置顶（与 Q21 不同的第二个成因）

Q21 修的是 `pinned_message` **服务消息**被清扫缓存误删。本条是另一个独立成因：**频道帖自动转发到关联讨论群的那条消息本身**被广告检测删掉。两者都表现为「频道置顶被取消」，但触发路径完全不同。

**根因**：频道发帖后，Telegram 会把它自动转发进关联讨论群，这条转发消息带 `is_automatic_forward: true`、`sender_chat`（来源频道）、`from`（Telegram 服务账号，如 `777000`，`is_bot` 为 falsy）。它有正文、没有 `pinned_message` 等服务消息字段，因此 `isTelegramServiceMessage` 挡不住；又因为有 `from` 且非 bot，会穿过入口早退进入广告检测。检测时 `resolveAdIdentityProfile` 把 `sender_chat`（频道）当作检测对象，**频道名/简介一旦命中广告身份判据，就删掉这条转发帖**——被删的若正是被置顶那条，Telegram 因置顶目标消失而自动取消置顶。关闭「信息署名」的频道，转发帖的 `from` 就是服务账号而非频道管理员，更易命中。

**关键区别**：这与内容像不像广告无关。哪怕频道发的是任意正常内容，只要频道资料命中判据，转发帖就会被删。所以修复不是「广告判据豁免」，而是从入口直接放行整类消息。

**修复内容**：新增 `isChannelAutoForward` 判定（唯一信号 = `is_automatic_forward === true` 且存在 `sender_chat`），在 `handleMessage` 最顶部单点早退——先于黑名单拦截、缓存、广告检测、命令分发的一切治理逻辑。频道自动转发帖不是群成员发言，一律不删、不缓存、不检测、不当命令。

**不牵连的场景**：真人以本群匿名管理员身份发言（`sender_chat.id === chat.id`）、真人用外部频道身份发广告（没有 `is_automatic_forward` 标记）——这两类没有该标记，行为不变。

**无需清库**：本条修复只改运行时判定，不涉及历史 D1 数据，升级后 `wrangler deploy` 一次即可，不必执行任何 SQL。

### Q24：正常用户被广告检测误封了怎么办

私聊 bot 发 `/pending` 找到那条快照的序号，再发 `/ignore 序号`。这一条命令会做四件事：**解除全群禁言**、移出 D1 黑名单（若首次命中，本就没拉黑，回执会写「本就不在黑名单」）、遍历所有配置群解封、给**所有命中该用户的指纹**累加一次误报计数，并把**本次判定读到的素材登记进误判放行库**。

误报计数不是记录用的，它会实际降低指纹置信度（置信度 = 命中数 / (命中数 + 误报数)）。跌到 `AD_FINGERPRINT_MIN_CONFIDENCE`（默认 0.6）以下的指纹不再参与判定；累计 3 次误报且置信度跌破 0.2 的 auto 指纹会被**自动退役删除**。所以每次 `/ignore` 都在让检测变准，纠错本身就是训练。

**误判放行库解决的是「同一个素材再被误判一次」**：`/ignore` 只做减法（删掉学错的东西），而被误判的那条消息/昵称/用户名/简介本身仍然参与后续判定 —— 同一个人再发一次同样的内容还会照同样的判据得同样的分。放行库把这次读到的素材直接标成「正常」，此后它们**不参与判定**。放行记录永久有效，`/allowlist` 可以查看（0 命中的排最前）并用 `/allowlist del 序号` 撤销。

如果快照已经过期（保留 1 小时），直接用 `/unban TGID` 解封 —— 但这样不会给指纹记误报、也不会登记放行库，同类误判还会再犯。所以建议养成每天看一次 `/pending` 的习惯。

**误封率持续偏高**时：先看 `/words` 找出误报数高的指纹用 `/delword` 删掉，再考虑调高 `AD_SCORE_THRESHOLD`。手工删几条脏指纹通常比调阈值有效得多。

### Q25：广告号没被检测到怎么办

三种手段，从快到慢：

1. **回复学习**（最快）：在群里回复那条广告消息，说「这是广告」或「封了他」。立即按广告处置，同时把该用户的昵称/简介/正文特征以 manual 来源学入指纹库。仅群管理员及以上可触发。
2. **`/addword`**：手工加一条精确指纹，例如 `/addword 收U秒结` 或 `/addword @promo_seller`。手动指纹恒为满权重满置信度，**永不被误报退役**。
3. **`/addsample`**：加一条 AI 语义样本，让相似表述也能被识别。需要绑定了 Workers AI 才生效。

补完指纹后，用 `/rescreen` 把观察窗口里的人拿新指纹库重新筛一遍 —— 之前分数不够放过去的人会被回溯处理。

**不建议直接调低 `AD_SCORE_THRESHOLD`**：指纹是精确匹配（归一化后完全相等且 ≥ 6 字），加指纹只影响命中它的人；降阈值影响所有人，误封会成片出现。

### Q26：`/adstats` 显示「未绑定，降级为评分 + 指纹两层」

说明 Workers AI 没绑上。检测仍在正常工作（前两层），只是少了语义相似度这一层，对**改写过表述的广告文案**识别率会低一些。

修法：走 `wrangler deploy` 部署的话，确认 `wrangler.toml` 里有 `[ai]` / `binding = "AI"`；在 Dashboard 粘贴代码部署的话，去 **设置 → 绑定 → 添加绑定 → Workers AI**，变量名必须**正好是 `AI`**。

绑好后再发 `/adstats`，应显示 `已绑定（@cf/baai/bge-m3 / 1024 维）`。接着发几次 `/warmup` 把向量补满 —— **「已生成向量」为 0 时第三层实际是空转的**。

> 曾有一版把模型名硬编码成 `@cf/baai/bge-base-zh-v1.5`，而 Cloudflare 目录里**没有这个模型**（bge 系列只有 `-en-` 三个尺寸与 `bge-m3`，无中文变体），导致每次调用都被 `Ai._parseError` 拒绝、日志里只有一串栈看不到原因。如果你看到 `[广告检测] 生成文本向量失败`，现在的日志会打出 `model=` / `name=` / `message=`，据此对照 [Workers AI 模型目录](https://developers.cloudflare.com/workers-ai/models/) 即可定位。

### Q27：广告检测的 11 张表建失败了会怎样

**既有功能完全不受影响。** `adDetectionReady` 返回 false 时整个广告层静默跳过，黑名单、`/ban`、`/spam`、`/unban`、自助解封、投票全部照常工作。

建表失败还会进入 **60 秒冷却** —— 这是刻意设计的：D1 抖动时如果每条消息都重试一遍建表，会把 Worker 的子请求预算耗光，反而拖垮正常功能。

诊断：第一主人私聊发任意广告命令（如 `/adstats`），会收到明确报错「广告检测数据表初始化失败，请稍后重试或检查 D1 绑定」。再去 Workers Logs 搜 `[广告检测]` 前缀看具体原因，最常见的是 D1 没绑定或绑定名不是 `DB`。

### Q28：`/admins` 里某个权限人显示「昵称:未获取 用户名:未获取」

**原因**：Telegram Bot API 的硬性限制 —— **bot 只能查询自己所在群的成员资料**，没有任何接口能凭 TGID 直接查任意用户的昵称和用户名。

能返回用户资料的接口只有三个，全部要求 bot 与目标同群：

| 接口 | 前提 | 说明 |
| --- | --- | --- |
| `getChatMember` | bot 是该群成员 | 查单个成员，`/admins` 的主力路径 |
| `getChatAdministrators` | bot 是该群成员 | 拉整份管理员列表 |
| `getChat` | —— | **只对群 / 频道有效**，传普通用户 TGID 拿不到昵称与用户名 |

所以只要这个人不在你任何一个 `GROUP_ID` 配置群里，`/admins` 就只能显示 TGID 加「未在配置群中获取到用户资料」。**这不影响权限判定** —— TGID 在 `OWNER_IDS` / `SUPER_ADMINS` 里就有权限，昵称只是给你看的标签。

**解决**（二选一）：

1. **让 bot 与其同群（推荐，资料永远是最新的）**：把 bot 拉进此人所在的任意一个群，再把该群 ID 加进 `GROUP_ID`。<br>**bot 不需要管理员权限，普通成员就够** —— `getChatMember` 只要求 bot 在群里。<br>⚠️ 两个注意点：① 加进 `GROUP_ID` 的群会一并受治理，**该群的 Telegram 管理员也就获得了 `/ban` `/spam` 权限**，不想开放就别加；② 资料是**每次命令实时查**的、没有持久化缓存，**bot 退群后立刻变回「未获取」**，想长期显示就得一直留在群里。
2. **用 `STATIC_USER_PROFILES` 填静态资料**：JSON 字符串，例 `{"197282502":{"first_name":"威廉","username":"RealNeoMan"}}`。<br>只作兜底：程序先用它填充，再调 API，**查到实时资料就自动覆盖静态值**，两条路互不干扰。适合权限人确实不方便进任何配置群的情况。<br>⚠️ 静态值是写死的，对方改了昵称不会自动更新，建议只填基本不变的 `username`。
